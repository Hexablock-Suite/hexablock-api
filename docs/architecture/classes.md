- Pages 2 to 4, `Domain`, `Use cases` and `Adapters`, hold one part each. A part page shows the types of its part in full. A grey box with the name only is a type of another part that one of its lines touches, and its eyebrow names the page that details it.
- A solid box is a type that exists in the code at `3a3b45a`. A dashed box with `«planned»` is design from the views of this page that the code does not have yet. It keeps the `«Sprint N»` of its view when the view gives one.

- `«dataType»` marks a type in the code that only carries data; it has no operations by design. `«module»` marks `AppModule`, a Nest module that only holds decorator metadata.

## How to read it

- The colored zone is the Clean layer, with the colors of [layers.md](layers.md): yellow for layer 1, purple for layer 2, light blue for layer 3 and dark blue for layer 4.
- One view can show several layers. The zones are bands, with the outer layer at the top and the inner layer at the bottom, so every dependency between layers points down.
- A dashed frame groups the classes of one GoF pattern or one group. Its label names the source, for example `STRATEGY · §3.3 · DS-6`. A frame is not a class. No line starts or ends on a frame. When two classes of different groups depend on each other, the line joins those two classes. A line from one frame to another frame would claim that every class of the first group uses every class of the second group, and that is usually false. The professor asked this about a frame-to-frame arrow in the session of 2026-11-03: «todas esas usan los tres bloques de abajo, a lo mejor la respuesta es no».
- A dashed frame labelled `Aggregate` marks the boundary of one aggregate. It encloses the root and its members: an internal entity, and each value object that the root holds, directly or through another member, such as the `UserId` of a `ProgressKey`. A receiver interface, a port, a use case, a domain service and another aggregate stay outside. Its dashes are longer and darker than the dashes of a pattern or group frame, and its label names the root and the decision that draws the boundary, for example `Aggregate · PlayerProgress · decision 2`. When a class that is not a member sits between the members, the frame turns a corner around it. As with any frame, no line starts or ends on it. Views 1.1, 1.2, 1.3, 1.5 and slice 1 draw one frame each, for `PlayerProgress`, `User` and `LevelDefinition`. Slices 2 and 3 draw the root as a full class with no member, so the frame encloses the root alone, and the footnote names the view of its members. A view that draws a root only as a reference box draws no frame: views 2.3, 3.2 and 3.5. View 1.4 draws `LevelResult`, a member of `PlayerProgress`, without its root, so it draws no frame either.
- The interface of a GoF pattern carries only `«interface»`, and the concrete classes of the pattern carry no role label and no tactical stereotype, as the professor draws them (class of 2026-11-14; design decision of 2026-11-15). The dashed frame of the pattern, or a note, names the pattern. No view shows a role label, such as `«Strategy»`, `«Decorator»` or `«Adapter»`. `«port»` marks an interface that an outer layer implements. `«repository»` marks a repository: the port in layer 2 and its adapter in layer 3. `«port»` and `«repository»` mark a layer, not a role of the pattern, so they also hold inside the frame of a pattern (decided on 2026-11-16 on [#139](https://github.com/Hexablock-Suite/hexablock-api/issues/139)). A domain class carries its tactical stereotype: `«entity»`, `«aggregate root»`, `«value object»` or `«domain service»`.
- An underlined member is static, as in UML.
- The dashed box at the top right of a class holds its type parameters. This is the UML template notation that §4.1 asks for.
- A `«bind»` label on a realization or an inheritance line names the type that each parameter takes, for example `«bind» TSection → FitSection`. A dashed line with an open arrowhead and a `«bind»` label joins a bound class to its template, for example `Range<CharacterCount>` to `Range<T>` in view 1.3.
- The teal class is the focal class of the view.
- A lollipop (a circle on a short line) is the input port that a use case implements.
- A dashed class with no members is a class that another view details. Its eyebrow names that view, for example `PART 2 · VIEW 2`.
- Under the name of a class, an ID such as `API-FR-04` names the requirement it serves.
- A filled diamond (composition) joins the root of an aggregate to each of its internal entities, on the side of the root. An internal entity exists only inside its aggregate, and only the root creates and changes it. The other end names the attribute and its multiplicity, even when it is 1. Any other attribute is a use arrow with the same role and multiplicity: a value object, the strategy of a context, the object that a decorator wraps, and a port. For example, `PlayerProgress` keeps its `LevelResult` values, and `LevelDefinition` holds its section, through use arrows. No hollow diamond appears. This follows the drawings of the classes of 2026-11-13 and 2026-11-14 (decision 13).
- A solid line with an open arrowhead is a use: the class depends on the other class. It points from the class that holds or calls to the class it needs. When the other class is an attribute that is not an internal entity, or an attribute across layers, the label names the attribute and its multiplicity. A port counts as across layers: it lives in layer 2, and its adapter lives in layer 3 or 4. When the other class is only a parameter, a return value, a local variable or a `new`, the label is a verb. A link that is none of these, such as a guard that a decorator applies or a class that a module only names in its metadata, gets no line; the box or the note names it. This follows the class of 2026-11-02 (decision 13), which replaces the diamond rule of the board of the class of 2026-10-02.
- The legend of each view lists only the line kinds that the view draws.
- The views do not mark which classes are planned. Today `src/` holds the user, progress and level classes of the domain with `Standing` and `LevelsCompleted`, the account and progress use cases with their ports, the `LeaderboardReader` port with `LeaderboardEntry`, `GetLeaderboardUseCase`, `AuthController` with `AuthDtoMapper`, `LeaderboardController` with `LeaderboardDtoMapper`, their adapters, the `LevelRepository` port with `DrizzleLevelRepository` and `LevelRowMapper`, the level use cases `GetLevelsUseCase` and `UpdateLevelsUseCase` with `LevelsController`, `LevelDtoMapper` and `LevelDto`, `LevelEditors`, `AuthorizeLevelEditorUseCase` and `LevelEditorGuard` (decision 18), `LoggingAspect` and `AppModule`. `TimingAspect` is planned.

## Data shapes

The team closed two data shape decisions on 2026-10-30. The app draws the same names on its side.

**DS-5: two tables for progress** (option «B · Dos tablas»). It serves API-FR-02 and API-FR-03.

| Table           | Key                           | Other columns                 | Read by                                   |
| --------------- | ----------------------------- | ----------------------------- | ----------------------------------------- |
| `progress`      | `userId`, `gameId`            | `highScore`, `updatedAt`      | sync, global leaderboard per `gameId`     |
| `level_results` | `userId`, `gameId`, `levelId` | `stars`, `moves`, `elapsedMs` | sync, per-level leaderboard for Fit, Sort |

**DS-6: one level schema, a common part and a typed section** (option «A · Común + sección tipada»). It serves API-FR-04.

| Part         | Fields                                              | Checked by                                                                                        |
| ------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Common       | `gameId`, `levelId`, `order`, `version`, `topology` | `LevelDtoMapper` (shape), then `GameId`, `LevelId`, `LevelOrder`, `LevelVersion` and `TopologyId` |
| Fit section  | `figure`, `pieces`, `witness`, `stars`              | `FitSection` (shape, and A5 on the `Topology` of the level)                                       |
| Sort section | `radius`, `goals`, `source`, `stars`                | `SortSection` (shape)                                                                             |

The Fit `stars` field is a list of `FitStarThreshold`, each one a `maxMoves` count and a `maxElapsedMs` time, and a Fit star needs both ([hexablock-app#60](https://github.com/Hexablock-Suite/hexablock-app/issues/60), 2026-11-06). The Sort `stars` field is a list of `Moves` limits, one `maxMoves` count per star (stars by moves, [hexablock-app#59](https://github.com/Hexablock-Suite/hexablock-app/issues/59), 2026-11-06). In both sections the stars are cumulative: star N needs star N-1. [`docs/level-format.md`](../level-format.md) gives the exact JSON of each field, with one complete example per variant (decision 4).

The API rejects a Fit level that fails A5: the piece areas differ from the figure area (`unequal-area`), or the witness does not place each piece once and cover the figure exactly (`inexact-witness`). `UpdateLevelsUseCase` checks every level before it saves any level.

**DS-4 is closed** (2026-11-06, [#24](https://github.com/Hexablock-Suite/hexablock-api/issues/24)). The best result of a level has more stars; on equal stars, fewer moves; on equal moves, less time. On a full tie, the stored result stays. `LevelResult.isBetterThan()` holds this order: it asks `Stars.isMoreThan()`, then `Moves.isFewerThan()`, then `ElapsedTime.isShorterThan()`. `PlayerProgress.recordLevel()` keeps the best result of each level (DS-12). The same order ranks the per-level leaderboard of Fit and Sort. The global leaderboard of Lines and Merge ranks by `Score.isHigherThan()`. The global leaderboard of Fit and Sort ranks by `Standing.isBetterThan()`: more total stars, then more levels completed, then fewer total moves, then less total time (S3-03, confirmed on 2026-11-16 on [#76](https://github.com/Hexablock-Suite/hexablock-api/issues/76)). `LeaderboardReader` only filters and sums, and `GetLeaderboardUseCase` orders the entries with these comparisons (decision 2).

| Abstraction                                    | Reason                                                                                                                   |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `UseCase<TRequest, TResponse>` and input ports | Layer boundary: the controllers depend on the interface (layers.md). One aspect wraps any use case (§3.5).               |
| Output ports (`ProgressRepository` and others) | Layer boundary (§3.4, Q10). The database engine row of §8.                                                               |
| `PasswordHasher`, `TokenIssuer`, `Clock`       | Layer boundary: the use cases do not read the system clock or a crypto library (API-NFR-11, rule R-deterministic-core).  |
| `Result<T, E>`                                 | A use case returns an expected failure as a value. No exception crosses the input port to the HTTP layer.                |

| `LevelValidator<TSection>`                     | DS-6: each variant picks its own section type. The section checks its shape and holds its rules, A5 for Fit (API-FR-04). |
| `Topology` and `Topologies`                    | D4, §8: a square, triangular or 3D topology. A5 asks the `Topology` of a level for its cells and steps (decision 6).     |
| `Range<T>`                                     | Credential limits (#60): one `Range<CharacterCount>` each for `Username`, `Password` and the HTTP adapter (D6, #99).     |

Plain classes: the row mappers, the HTTP mappers, the controllers, `LevelDto`, the guard and the filter. `LeaderboardEntry<TResult>` is a response type of layer 2 in `src/application/ports/`, with no tactical stereotype. It holds the `UserId` of the player and the domain value that ranks the player: a `LevelResult`, a `Score` or a `Standing`. It has no rule of its own, because the order of each board lives in that value object of the domain (decision 2). `PlayerProgressReceiver` and `UserReceiver` are receiver interfaces of the domain with no tactical stereotype: each aggregate delivers its parts to one of them, as a value object delivers its datum, and only the border implements them (decisions 2, 15 and 16). `ProgressKeyReceiver` is the same kind of interface for the two parts of a `ProgressKey`. Through them each aggregate gives its state to the border, as the Memento of decision 2 asks. `ProgressKeyValues`, `ProgressValues` and `UserValues` in `src/adapters/received.ts` hold the plain values that the border receives; they are types of the border, not of the domain. `LevelValidators` is not a plain class: it is a «domain service» that picks the strategy of an incoming level by its `gameId`, outside any level, and keeps no state that changes (decision 5). The composition root fills it, so it needs no interface of its own.

## Domain design rules

These rules say how the domain model must be. They apply to every class of `src/domain/`, built or planned, and to the class views that draw it. They come from the classes of 2026-11-13 and 2026-11-14 and from the design decisions of the team of 2026-11-15. When the code does not follow a rule yet, the code changes, not the rule. Rule R-domain-design of `AGENTS.md` points to this section.

### Aggregates

- **The root is the only door.** Code outside an aggregate sends every message to its root. No public method of the root returns an internal entity or another aggregate. Only data in domain types leaves the aggregate, never a part that the caller can change (classes of 2026-11-13 and 2026-11-14).
- **Invariants hold after each operation.** When an operation on the aggregate ends, every invariant of the aggregate holds. The boundary of the aggregate encloses the true invariants of the business (class of 2026-11-13).
- **Global identity only in the root.** The system identifies the root of an aggregate in one universal way. An internal entity has a local identity: it has a meaning only inside its aggregate (class of 2026-11-13). The factory of the aggregate builds that local id from the identity of the root, and it asks no id generator for it (design decision of 2026-11-15).
- **One repository per aggregate.** Each aggregate has its repository in the design, also when its adapter keeps the data in memory. The port carries the name of the aggregate, and it saves and finds the whole root with its parts. No repository exists for an internal entity or for another part of an aggregate (classes of 2026-11-13 and 2026-11-14).
- **One aggregate per transaction.** A transaction changes one aggregate. A use case can read many aggregates, but each transaction changes only one of them. Outside the boundary of an aggregate, the system accepts eventual consistency. If one operation must change two aggregates at the same time, the boundary is wrong (classes of 2026-11-13 and 2026-11-14). When one request changes several aggregates, the use case checks all of them first. Then it saves each aggregate in its own transaction (design decision of 2026-11-15).
- **Reference by identity.** An aggregate refers to another aggregate only by the identity that the system gives to the other root. It never holds the other aggregate, and it never refers to it by a business key that can change, such as a username. If an aggregate needs data of another aggregate, it keeps a local view with only that data. That view can be out of date for a short time (class of 2026-11-13).
- **Events, not questions.** An aggregate never asks another aggregate for data. It tells its changes through domain events, and each listener reacts. The root only records its events. A use case delivers them after the change (class of 2026-11-13; design decision of 2026-11-15).
- **Small aggregates.** An aggregate holds the true invariants of the business and no more, so it stays small. A value object is never the root of an aggregate. Two concepts that the business defines separately never share one aggregate (class of 2026-11-13).

### Domain services

- A domain service is a business operation of the domain layer that does not belong to an entity, a value object or an aggregate (class of 2026-11-13).
- First, try to put the operation in an aggregate. The operation does not go there if it must load other aggregates or create objects of another aggregate. It is a domain service only when no aggregate can hold it (class of 2026-11-13).
- A domain service has no state. It has one public method, which takes and returns domain objects. Private methods can help it (class of 2026-11-13).
- Its name and the name of its method use verbs of the language of the game. A name such as `ProgressHelper` or `LevelManager` is wrong (class of 2026-11-13).
- It receives entities and value objects that are already loaded, applies the rule and returns a result. It never calls a repository, it opens no transaction, and it never touches the infrastructure (classes of 2026-11-13 and 2026-11-14).
- The rules of each aggregate stay inside the aggregate. A domain service only coordinates what no aggregate can do alone (class of 2026-11-13).
- A use case is an application service, not a domain service. It loads the aggregates through their repositories, asks the domain, and saves the one aggregate that changed (classes of 2026-11-13 and 2026-11-14).

### Values, time, orders and names

- **Value objects are immutable.** A value object keeps each field private and `readonly`, it has no setter, and an operation that gives a different value returns a new value object (class of 2026-11-14).
- **One failure mechanism.** The factory of every value object returns a `Result`: a datum that breaks the rule gives a failed `Result`, never an exception (design decision of 2026-11-15). A factory that no datum can fail returns the value itself, and a factory that a datum can fail keeps returning a `Result` (decided on 2026-11-16 on [#139](https://github.com/Hexablock-Suite/hexablock-api/issues/139)). `LevelResult.of()` and `ProgressKey.of()` return the value itself (decisions 2 and 3, [#148](https://github.com/Hexablock-Suite/hexablock-api/issues/148)). The failure carries a code for the broken rule, and the border writes the message. Only a guard against a programming defect, such as a missing argument, can still throw. This is the mechanism of decision 11.
- **The border builds the domain values.** An adapter of layer 3, such as a DTO mapper, builds the domain values from the request. A use case receives domain values, and it never builds a domain value from a loose primitive (design decision of 2026-11-15). This extends decision 12 to every use case.
- **Time is a value object.** The domain model holds no `Date`: no field, parameter or return value in `src/domain/` is a `Date` (class of 2026-11-14). The value object of a time takes its name from the language of the game, for example the instant of a sync. Each time concept with a different meaning has its own value object. A general name, such as `Instant`, is correct only when the domain has one meaning of time (design decision of 2026-11-15). Today the domain has one time concept, the instant of a sync, and its value object is `SyncInstant` (decision 3).
- **Each ranking order lives in the domain.** An order that ranks domain objects, such as the order of a leaderboard, lives in one value object of the domain, which compares two of them. A reader port only filters and sums. The use case orders with the comparisons of the domain, and the adapter adds no order (design decision of 2026-11-15). This applies the rule of decision 2 to every ranking: the rules stay in the domain, and the adapter adds none.
- **Names from the language of the game.** A domain class and its public operations take their names from the language of the game, not from a technique or a pattern. A technical name is correct only for a technical device, such as the receiver interface of decision 15 (classes of 2026-11-09 and 2026-11-13).

1. **Ports in the application layer.** The class of 2026-10-30 answered Q10: the ports belong to the application layer. 2. **One progress aggregate over two tables (DS-5).** The domain comes first: `PlayerProgress` is the aggregate root, one per `userId` and `gameId`. Its identity is the `ProgressKey` value object ([#107](https://github.com/Hexablock-Suite/hexablock-api/issues/107)): it holds the `UserId` and the `GameId` in private fields, `equals()` compares both, and `deliverTo(receiver: ProgressKeyReceiver)` gives both to a receiver of the border in one call. `ProgressKey.of(userId, gameId)` takes the two value objects built and returns the key itself (rule «One failure mechanism», [#148](https://github.com/Hexablock-Suite/hexablock-api/issues/148)). Each one guards its own rule, and any user can have a progress in any game, so no pair of valid parts breaks a rule, and the factory has no failure to give. `SyncProgressUseCase`, `GetProgressUseCase` and `ProgressRowMapper` use the key that it returns. The day a rule joins a user and a game, `ProgressKey.of()` becomes a `Result` factory with its own failure code. An argument of another type is a defect of the caller, so its guard throws a `TypeError`. `PlayerProgress` holds one `ProgressKey`, and `PlayerProgress.equals()` compares the two keys. The name `ProgressKey` is provisional until the team reviews it. Views 1.1, 2.2 and 3.1, slice 1 and the sync progress sequence of [flows.md](flows.md) draw the key and the port signatures. It keeps its `LevelResult` values and is the only way to record one, so `LevelResult` has no repository and no `userId` or `gameId` of its own. `LevelResult` has no public field either: its four value objects are private, `LevelResult.of()` takes them built, and `LevelResult.deliverTo()` gives them to a receiver of the border (decision 3). `ProgressRepository` reads the whole aggregate with `find(key)` and changes it with `update(key, change)`: both take the `ProgressKey`, which the use case builds from the `userId` and the `gameId` of its request. `update()` holds a lock for the key, passes the stored aggregate or `null` to the change, and saves the whole aggregate that the change returns. So two overlapping syncs of one key run one after the other. The rules, such as the highest score, stay in the domain; the adapter adds none. `DrizzleProgressRepository` splits it into the two tables of DS-5: `progress` keeps one row per `userId` and `gameId`, and `level_results` keeps `userId`, `gameId`, `levelId`, `stars`, `moves` and `elapsedMs`. The aggregate keeps only the best result of each level (DS-12) by the order of DS-4: `recordLevel()` keeps a new result only when `LevelResult.isBetterThan()` ranks it above the stored one. The aggregate has no getter, no public field and no snapshot type (design decisions of 2026-11-09 and 2026-11-15). `PlayerProgress.deliverTo(receiver: PlayerProgressReceiver)` gives its parts to a receiver of the border in one call, as a value object delivers its datum (decision 15): the `ProgressKey`, the `Score` or `null`, the `SyncInstant` of `updatedAt` and a new list of the `LevelResult` values. The values are immutable and the list is new, so a change to what the receiver gets does not change the aggregate. `ProgressRowMapper` and `ProgressDtoMapper` receive the parts through `receiveProgressOf()` of `src/adapters/received.ts`, which also receives the `userId` and the `gameId` of the key through `receiveProgressKeyOf()`, receives the four values of each `LevelResult` and builds a `Date` from the milliseconds that the `SyncInstant` delivers. `DrizzleProgressRepository` builds its lock key `<userId>:<gameId>` and its SQL filters from `receiveProgressKeyOf()`, so the lock key text and the SQL are the same as before the key, and the in-memory repository of the tests builds its map key the same way. `PlayerProgress.restore(key, highScore, updatedAt, results)` builds the aggregate again from the delivered parts, in the order of the receiver: it checks the key and the instant as `start()` does, and it records the high score and the results with the rules of `recordScore()` and `recordLevel()` at the stored instant, so `updatedAt` stays the stored instant ([#97](https://github.com/Hexablock-Suite/hexablock-api/issues/97)). No type parameter stands for the instant, and no `Date` enters the domain (decision 3). This is the Memento of Millett and Tune: the aggregate hides its state and delivers it to the border, and the repository maps it to the data model (views 1.1, 3.1 and 3.5). The aggregate keeps its results in a list and finds the stored result of a level with `LevelResult.isForSameLevelAs()`, which compares two `LevelId` values with `equals()`. It keeps no map with a text key taken out of the `LevelId` (design decision of 2026-11-09); a game has few levels, so the list is enough. The order of the leaderboards lives in the domain too (design decision of 2026-11-15, section «Domain design rules»): `LevelResult.isBetterThan()` ranks the board of a level (DS-4), `Score.isHigherThan()` ranks the global board of Lines and Merge, and `Standing.isBetterThan()` ranks the global board of Fit and Sort (S3-03). `LeaderboardReader` only filters and sums. `DrizzleLeaderboardReader` reads the `progress` and `level_results` tables, filters by `gameId` and by level, sums the totals of each player, and adds no order; it names no table or column of the user module. `GetLeaderboardUseCase` orders the entries with the comparisons of the domain. Two names come from the words of S3-03. The value object for «levels completed» is `LevelsCompleted`: it counts the stored results of a player in one game, so a level counts once (DS-12). A row of a global board is a `LeaderboardEntry<Score>` for Lines and Merge and a `LeaderboardEntry<Standing>` for Fit and Sort: one generic entry serves the three boards, and its type argument is the domain value that ranks the row, so no row carries a nullable field of another board. `Standing` holds four totals: a `Stars`, a `LevelsCompleted`, a `Moves` and an `ElapsedTime`. A board lists only the players that have something to rank: a stored result of the level, a high score, or at least one completed level, because `Standing.of()` fails with `no-level-completed`. The entry names the player by its `UserId`. A later player name is an added field, filled through a port of the user module.
3. **The progress row fields (proposal).** DS-5 fixes the key. `highScore` and `updatedAt` are our proposal: the app keeps a high score for Lines and Merge, and the use case reads the instant from the Clock port and passes it to the domain. `updatedAt` is the instant of the last sync of the progress, and its value object is `SyncInstant`, a name from the language of the game (design decision of 2026-11-15; built, [#97](https://github.com/Hexablock-Suite/hexablock-api/issues/97)). `SyncInstant.of()` takes the milliseconds since the Unix epoch and guards the rule of a valid instant: a whole number of milliseconds inside the range of a JavaScript `Date`. A number that breaks it gives a failed `Result` with the code `invalid-sync-instant`. `SyncInstant.isLaterThan()` compares two instants. The `Clock` port gives a `SyncInstant`, which `SystemClock` builds, and `SyncProgressUseCase` passes it to `start()`, `recordScore(score, at)` and `recordLevel(result, at)`, so the use case checks no instant. Each record moves `updatedAt` to the instant of its sync, and the aggregate keeps `updatedAt` from moving back: a record with an earlier instant leaves it, and a sync that records nothing leaves it too. `PlayerProgress` keeps the `SyncInstant` in a private field, so no field, parameter or return value of the progress is a `Date` or a number of milliseconds. The `updated_at` column keeps a timestamp, and the JSON bodies keep the same ISO 8601 text as before: `receiveProgressOf()` builds the `Date` of the row and of the body, and `ProgressRowMapper` builds the `SyncInstant` of a stored row; a stored instant that breaks the rule, such as `infinity`, is a server fault (decision 11). In the domain the high score is a `Score` value object, not a number (design decision of 2026-11-09: no primitive crosses a public signature of the domain model, the boolean and the delivery of decision 15 excepted). `Score.of()` guards the rule: a score is a non-negative safe integer, and a number that breaks it gives a failed `Result` with the code `invalid-score` (decision 11). `Score.isHigherThan()` tells which of two scores wins, and `PlayerProgress.recordScore()` keeps the higher one. A progress with no score yet holds `null`, so it differs from a score of 0. The `high_score` column and the JSON bodies keep a number: only `ProgressRowMapper` and `ProgressDtoMapper` receive the number of a `Score` (decision 15), and `ProgressDtoMapper` builds the `Score` of a sync from the body. The same decision holds for a level result (view 1.4): `LevelResult` holds a `LevelId`, a `Stars`, a `Moves` and an `ElapsedTime` value object, not a string and three numbers. `LevelId.of()` guards a non-blank text. `Stars.of()`, `Moves.of()` and `ElapsedTime.ofMs()` each guard a non-negative safe integer, and `ElapsedTime` counts milliseconds. Each factory returns a `Result` with the code of its rule: `invalid-level-id`, `invalid-stars`, `invalid-moves` or `invalid-elapsed-time`. Each one compares by value with `equals()`. The `level_results` columns and the JSON bodies keep text and numbers, so only the border builds and receives these value objects ([#95](https://github.com/Hexablock-Suite/hexablock-api/issues/95)). `LevelResult` keeps the four in private fields and has no getter. `LevelResult.of(levelId, stars, moves, elapsedTime)` takes the four value objects and checks nothing more, so it takes no raw value, cannot fail and returns the `LevelResult` itself. `ProgressDtoMapper` builds the four from the body, and `ProgressRowMapper` and `DrizzleLeaderboardReader` build them from a `level_results` row. All three call `buildLevelResult()` of `src/adapters/built.ts`, which combines the four `Result` values in the order of the fields and gives the first failure ([#103](https://github.com/Hexablock-Suite/hexablock-api/issues/103)). `LevelResult.deliverTo(receiver: LevelResultReceiver)` gives the four value objects to a receiver of the border in one call, as `Standing.deliverTo()` gives its four totals. The helper `receiveLevelResultOf()` of `src/adapters/received.ts` receives them as `LevelResultValues`, the text and the three numbers of a row or a body; that type lives in the border, not in the domain. The four names are provisional until the team reviews them with the app.
4. **One generic level type, born valid (DS-6, S3-02; built, [#77](https://github.com/Hexablock-Suite/hexablock-api/issues/77)).** `LevelDefinition<TSection>` holds the common part of DS-6 (`gameId`, `levelId`, `order`, `version` and `topology`) and a section, and `TSection` is `FitSection` or `SortSection`. A level is born valid: `LevelDefinition.of()` takes the values of the common part and the `Result` of the section factory, and it returns a `Result`. Each section checks its own shape when it is created (`FitSection.of()`, `SortSection.of()`), so no level with an unchecked section exists in the domain, and `AnyLevel` is gone. The unchecked JSON stays in `LevelDto`, in layer 3. A list of levels of several games has the type `LevelDefinition<unknown>`: each section is valid, and only the strategy of its game knows its type. `LevelDefinition` is an «entity» and the «aggregate root» of one level. Its identity is the `gameId` plus the `levelId`, and it has its own repository, `LevelRepository` (built, [#80](https://github.com/Hexablock-Suite/hexablock-api/issues/80)). The section is a value object, so it has no repository. Why one level is the boundary: the section rules hold inside one level (its shape now, and A5 for Fit with #79), and the version rule of S3-10 compares two copies of the same level, the stored copy and the incoming copy. No requirement links two levels: DS-6 defines one level, DS-11 compares two copies of one level, S3-02 fixes the format of one level, and S3-10 rejects a lower `version` of one level. So a bigger aggregate, such as every level of a game, would enclose no true invariant, and a smaller one would split the version rule from the level that it protects. The version rule lives in the root (#80): `stored.accepts(incoming)` returns a `Result`. It rejects a copy with a lower `version` with the level problem `older-version`, and it gives the incoming copy for an equal or a higher `version`, so a retry of the same update is safe. A copy of another level is a defect of the caller, so `accepts()` throws. `isIdentifiedBy(gameId, levelId)` tells if a level has that key. `LevelRepository.update(gameId, levelId, change)` holds an advisory lock for the `gameId` and the `levelId`, passes the stored state of the level to the change (absent, valid, or broken for a row that breaks a rule, [#147](https://github.com/Hexablock-Suite/hexablock-api/issues/147)), and saves the level that a successful change returns, one level per transaction, as `ProgressRepository.update()` does (decision 2). The change runs `accepts()` again under that lock, so an update that races another one cannot save an older level, and the adapter adds no rule. A change that returns a level with another key saves nothing, because the lock covers only its own key. `list()` gives every stored row by `gameId` and then by `levelId`: the valid levels and the broken rows apart (decision 19). The level has no getter: `deliverTo()` gives its common part and its section to a receiver of the border (decision 6). `UpdateLevelsUseCase` checks every level first and then saves each level in its own transaction (section «Domain design rules»). The shared level format is [`docs/level-format.md`](../level-format.md): the fields and their rules, one complete Fit example and one complete Sort example. The app writes its level files in it (hexablock-app#166 and #167), and the level tests of #77, #78 and #79 read their fixtures from it. It codes S3-02 of [#76](https://github.com/Hexablock-Suite/hexablock-api/issues/76), confirmed on 2026-11-16. Lines and Merge have no level files (API-FR-04). View 1.2 draws the level and its strategies, and view 1.5 draws its values.
5. **`LevelValidators`, a domain service that picks the strategy by `gameId` (built, #77).** `LevelValidator<TSection>` stays the Strategy of each variant with level files (§3.3, DS-6), but it holds no rule. The section checks its own shape and holds its own rules, so `isSection()` is gone. The strategy only picks the section type: `sectionOf(raw, topology)` asks its section type to read the section as it arrives, and it passes the topology to the rules that need it, such as A5 (decision 6). `SortLevelValidator` implements it for Sort (built, [#78](https://github.com/Hexablock-Suite/hexablock-api/issues/78)): `sectionOf()` returns what `SortSection.of()` gives, and it does not pass the topology on, because no rule of the Sort section needs it. `SortSection` holds the rules of the Sort section: exactly its four fields, a radius and a goal of 1 or more, one of the two kinds of source, and one star threshold or more, each one a `Moves` limit. So a negative threshold gives the level problem `invalid-stars`, never a thrown error. `FitLevelValidator` implements it for Fit (built, [#79](https://github.com/Hexablock-Suite/hexablock-api/issues/79)): it holds `Topologies`, finds the `Topology` of the level and returns what `FitSection.of(raw, topology)` gives (decision 6). `LevelValidators` keeps a small list of entries, one `GameId` and its strategy for each variant with level files, and it finds the strategy of a `gameId` with `GameId.equals()`. It keeps no `Map`: a JavaScript `Map` compares object keys by reference, so two equal `GameId` values would be two keys, and decision 2 rejects a map keyed by a value taken out of a value object. The composition root builds it once with `LevelValidators.of(entries)`. Two entries for one game are a defect of the composition root, so the factory throws. `check()` takes the values of the common part and the section as it arrives, asks the strategy for the section, and builds the level with `LevelDefinition.of()`. A `gameId` with no entry has no level files, so `check()` returns the level problem `game-without-levels`. Why a «domain service»: it picks the strategy from the `gameId` of an incoming level, before and outside any `LevelDefinition`, so no aggregate can hold this choice. It keeps no state that changes: its entries are fixed when the composition root builds it (class of 2026-11-13, section «Domain design rules»). `LevelDtoMapper` builds the values of the common part and passes the section as it arrives. A mapper never picks a section type. `LevelRowMapper` restores a stored row the same way (built, #80): it builds the values of the common part from the row and passes the stored section to `LevelValidators.check()`, so the strategy of the row's `gameId` builds the section. No unchecked section enters the domain, also from the database. A row that no strategy accepts is a broken row, not a level: `toStoredLevel()` gives the code of its first broken rule and its stored version, or no version when the version column breaks the rule of `LevelVersion` (decision 19). The mapper reads the `gameId` of a row only to build the `GameId` that `check()` takes, and it names no section type, so a new variant changes no mapper. `GameId` is an open value object, not a closed list. So a new variant with level files adds a section type, a strategy and one entry in the composition root, and it changes no existing class.
6. **Coordinates as value objects, rotation from the topology (built, #77 and #79).** A coordinate is a `Coordinate` value object: a list of one safe integer or more, not a tuple of numbers. The `topology` of the level, a `TopologyId`, says how to read it: the hex topology reads `[q, r]` as axial coordinates. `TopologyId` is an open lowercase slug, so a square, triangular or 3D level (§8, D4) needs no new schema, and the API never rejects a level only because its topology is not hexagonal. The A5 check rotates pieces, and the rotation steps come from the topology: a `Rotation` counts steps, never degrees, and the hex topology has six steps of 60°. `Topology` is an interface of the domain with two rules: `holds(cell)` tells if a `Coordinate` is a cell of the topology, and `turn(cell, rotation)` turns a cell around the origin. `HexTopology` implements it with no state: a hex cell has two values, and one step turns `[q, r]` to `[-r, q + r]`, as [`docs/level-format.md`](../level-format.md) says. A rotation turns only the steps left after its whole turns, so a negative count turns the other way and a large count runs no long loop. `Coordinate.turnedBy()` and `Coordinate.movedBy()` do the arithmetic of the cells, so no code outside `Coordinate` reads its values. `Topologies` is the small collection of the known topologies: one entry per topology, a `TopologyId` and its `Topology`. It finds a `Topology` with `TopologyId.equals()` and keeps no `Map`, because a JavaScript `Map` compares object keys by reference. It is a «domain service», as `LevelValidators` is (decision 5): the composition root builds it once with `Topologies.of(entries)`, two entries for one topology throw, and it keeps no state that changes. `FitLevelValidator` holds it, finds the `Topology` that the `topology` field names and passes it to `FitSection.of(raw, topology)` (#79). A level whose topology has no entry gives the level problem `unknown-topology`. The cells of `figure`, `pieces` and `witness` are `Coordinate` values, and a cell that the topology does not hold gives `invalid-figure`, `invalid-pieces` or `invalid-witness`. Then `FitSection` checks A5 on the witness and runs no search: the witness places each piece once, the covered cells have the area of the figure, and each covered cell lies in the figure once. A failure gives `inexact-witness` or `unequal-area`, so equal areas alone never pass, and no `FitSection` that fails A5 exists. The other numbers of the common part are value objects too: `order` is a `LevelOrder`, and `version` is a `LevelVersion`, whose `isOlderThan()` serves DS-11 and the version rule of S3-10. The parts of the sections are value objects as well (`FitPiece`, `PieceId`, `Placement`, `FitStarThreshold`, `BoardRadius`, `GoalCount`, `StackSource`, `Seed` and `TileColor`), and the star limits are `Moves` and `ElapsedTime`. The JSON keeps numbers and text at the border. Every class of the level schema is born with private fields, and the factory of each value object returns a `Result`, never an exception (rule «One failure mechanism»). `Moves.of()` and `ElapsedTime.ofMs()` return a failed `Result` too (#103), and the readers of the star limits turn it into the level problem `invalid-star-threshold`: a bad level file gives a level problem, never a server error. Since #80 the level and the composite values of its sections deliver their parts to a receiver of the border, each in the fields that its factory reads: `LevelDefinition.deliverTo()` gives `gameId`, `levelId`, `order`, `version`, `topology` and `section`, `FitSection` gives `figure`, `pieces`, `witness` and `stars`, `SortSection` gives `radius`, `goals`, `source` and `stars`, and `FitPiece`, `Placement`, `FitStarThreshold` and `StackSource` give their own fields. Each part then delivers its own value. `receiveJsonOf()` in `src/adapters/received.ts` runs these deliveries and gives the JSON of the shared level format. So `LevelRowMapper` writes the section column without a section type, and #81 can build the DTO the same way. No operation returns a part, and no delivery runs in the domain.
7. **One generic input port.** Every input port of [layers.md](layers.md) binds `UseCase<TRequest, TResponse>`, for example `SyncProgress`. One aspect class then wraps any use case (§3.5). The app makes the same choice (its decision 9). The cost: an input port cannot add a second method. The three account ports bind it too ([#104](https://github.com/Hexablock-Suite/hexablock-api/issues/104)): `RegisterUser` binds `UseCase<RegisterUserRequest, Result<UserId, RegisterProblem>>`, `Login` binds `UseCase<LoginRequest, Result<SessionToken, LoginProblem>>` and `AuthenticateToken` binds `UseCase<SessionToken, Result<UserId, TokenProblem>>`, so no input port declares an `execute()` of its own. Every problem type is an object with a `kind`: `LoginProblem` is `{ kind: 'invalid-credentials' }`, `TokenProblem` is `{ kind: 'invalid-token' }`, and `RegisterProblem` already had one; since [#105](https://github.com/Hexablock-Suite/hexablock-api/issues/105) it is only `{ kind: 'username-taken' }`, because the request carries values that follow their rules (decision 12). So `LoggingAspect` can wrap every input port. A unit test wraps each account port in it; `AppModule` does not wrap them, and the HTTP answers do not change. `GetLevels` binds it with `TRequest → void` and `TResponse → Result<ListedLevels, never>`: one call gives every valid level and every broken row apart (decision 19), and the read has no expected failure. `UpdateLevels` binds it with `TRequest → UpdateLevelsRequest` and `TResponse → Result<void, InvalidLevels>` (built, [#81](https://github.com/Hexablock-Suite/hexablock-api/issues/81)). `LoggingAspect` asks for a `kind` on the error type, and both error types meet it, so the aspect can wrap both. `AppModule` wraps `UpdateLevels`, as it wraps `SyncProgress`. `GetLeaderboard` binds `UseCase<LeaderboardQuery, Result<Leaderboard, never>>`: one input port serves both leaderboard routes, because `LeaderboardQuery` names the global board or the board of one level. The read has no expected failure, so its error type is `never`, and `AppModule` wraps it in `LoggingAspect`, as it wraps `SyncProgress` and `UpdateLevels` (decision recorded on [#83](https://github.com/Hexablock-Suite/hexablock-api/issues/83#issuecomment-6905667403)).
8. **No Abstract Factory in the API.** In the API, a variant has one product: its level validator. A factory per variant would wrap one constructor. To check with the team: whether the professor expects the pattern in the backend too.
9. **Port names in the language of the game.** A port says what the use case asks for, not how the data travels. For example, `LeaderboardReader`, not a name that says SQL or HTTP. A name that says how the data travels couples the use case to that technology, as the class of 2026-10-30 explained.
10. **Aspects in layer 2, behind a `Logger` port.** In the session of 2026-11-06 the professor answered Q12: the aspects talk to the use case, so they belong in the application layer, built as decorators with one interface common to the use cases, without libraries. `UseCaseAspect` and `LoggingAspect` live in `src/application/aspects/`. `LoggingAspect` writes to the `Logger` port in `src/application/ports/logger.ts`, so `src/application` stays free of Nest. The port takes a typed entry (the use case name, the outcome, and the `kind` of a failure or the name, the string `code` and the stack frames of a thrown error), never a prebuilt `message: string`. A fourth entry, `unavailable-level`, gives the `gameId`, the `levelId` and the reason code of a stored level row that breaks a rule; `GetLevelsUseCase` writes it, and `NestLogger` writes it at warn level with each key quoted as JSON (decision 19). `NestLogger` in `src/infrastructure/logging/` implements the port and writes the text. A failure logs only its `kind`, because the rest of a failure can hold values that the client sent. A thrown error never logs its message, for the same reason: the frames leave out the first line of the stack, which repeats the message, and a thrown value that is not an `Error` logs only its type ([#67](https://github.com/Hexablock-Suite/hexablock-api/issues/67)). The class of 2026-11-02 said that the message «no debería estar allí … En la implementación de este señor, en un adaptador secundario».
11. **Expected failures as values.** A use case never throws a domain error to the HTTP layer. `UpdateLevels` returns `Result<void, InvalidLevels>` (built, #81). `InvalidLevels` is `{ kind: 'invalid-levels', problems }`. Each problem is a `LevelProblemReport`: the `GameId` and the `LevelId` of one level and the `LevelProblem` code of the rule that it breaks, so a client knows which level to fix. The `kind` lets `LoggingAspect` log the failure without a value of a level. `LevelsController` turns a failed result into the error body of API-FR-06: a 400 with one detail per problem, which `LevelDtoMapper.toDetails()` writes. `HttpErrorFilter` handles only unexpected errors, with the same body shape. A stored level that breaks a rule is not a server fault: `GET /levels` answers 200 with the other levels and names the broken one in `unavailable` (decision 19). The factory of every value object returns a `Result` as well, so the domain has one failure mechanism (design decision of 2026-11-15, section «Domain design rules»; built, [#103](https://github.com/Hexablock-Suite/hexablock-api/issues/103)). A raw value that breaks the rule gives a failed `Result` with the code of the rule, such as `invalid-game-id`, `invalid-score` or `invalid-user-id`, and never an exception. The receiver interface is a technical device, and a technical name is acceptable there (classes of 2026-11-02 and 2026-11-09). 19. **A stored level row that breaks a rule (built, [#147](https://github.com/Hexablock-Suite/hexablock-api/issues/147)).** Decided by Oscar on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) («`PUT /levels` can replace the bad row») and on 2026-11-17 on #147 (option C for the read). A `levels` row that no strategy accepts is a broken row, not a level and not a server fault.
    - **The read under the lock tells three states apart.** `LevelChange` takes a `StoredLevel`, a closed union: `absent` (no row), `valid` (the restored `LevelDefinition`) or `broken` (the code of the first broken rule, a `StoredLevelProblem`, and the stored `LevelVersion`, or `null` when the version column breaks the rule of `LevelVersion`). So a broken row never passes as no row. `LevelRowMapper.toStoredLevel()` builds the valid and the broken states; the repository builds `absent`.
    - **The update replaces the broken row.** The version rule of S3-10 still holds over a broken row when its stored version is valid: the incoming level replaces the row when its version is equal or higher (`LevelDefinition.isOlderThan()` is false), and a lower version saves nothing and gives the level problem `older-version`. An equal version passes, so the same packaged level replaces its broken row. When the stored version itself breaks its rule, there is no version to compare, and any valid version replaces the row. Over a valid stored level, `accepts()` runs as before.
    - **The read hides no level.** `LevelRepository.list()` gives `ListedLevels`: the valid levels and the broken rows apart, each `UnavailableLevel` with the `gameId` and the `levelId` of its row as text and the reason code. `GetLevelsUseCase` logs one `unavailable-level` entry per broken row through the `Logger` port, with the same three values and no section (decision 10). `GET /levels` answers 200: `levels` holds the valid levels, and the optional `unavailable` field of `LevelsDto` names each broken row with its `gameId`, `levelId` and `reason`. The field is absent when no row is broken, so the answer keeps its old shape.

20. **The board of a level that the definitions do not hold answers 404 (built, [#146](https://github.com/Hexablock-Suite/hexablock-api/issues/146)).** Decided by Oscar on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) (question 1, option B, with the API holding every level).
    - **One query on the level port.** `LevelRepository.holds(gameId, levelId)` answers whether a row is stored for the key. A valid row and a broken row (decision 19) both answer true: a broken row is still a level that the definitions hold, so its board exists. The query takes no lock and restores no level. `DrizzleLevelRepository` reads one key column of at most one row; the in-memory fake and the shared contract pin the same answers.
    - **A named failure of the use case.** `GetLeaderboardUseCase` holds `LevelRepository` next to `LeaderboardReader`. For a level query it asks `holds()` first and returns the failed `Result` `UnknownLevel` (`{ kind: 'unknown-level' }`) with no read of the results. The global board never asks it: any `gameId` keeps its global board (decision 5). `LoggingAspect` logs the kind of the failure.
    - **The border answers 404.** `LeaderboardController` turns `unknown-level` into a `NotFoundException` with the message `No level <levelId> for gameId <gameId>`, and `HttpErrorFilter` answers it with `ErrorDto` (API-FR-06). `openapi/openapi.json` lists the 404 of the level route.
    - **The bundled levels.** The API holds every level, the levels that the app bundles too. A deploy step that loads them is [#158](https://github.com/Hexablock-Suite/hexablock-api/issues/158); until it runs, the board of a bundled level that the API does not store answers 404.

    Views 2.2, 2.3, 3.2 and slice 3 draw `holds()`; view 2.2 draws the use arrow `levels 1` from `GetLeaderboardUseCase` to `LevelRepository`.

## Render the images

The views come from the HTML files in [`classes/views/`](classes/views/). Each file holds one inline SVG drawn with the diagram-design skill and the HexaBlock profile. Open the file in a browser to see the drawing. The `.png` image next to it is that SVG rendered at scale 2 by a headless browser. After you edit a file, export the image again with `/diagram-design:export-diagram docs/architecture/classes/views/<view>.html --png-only`, then run `pnpm format`. The formatter changes the HTML layout only; the drawing stays the same. Commit each `.html` file together with its `.png` image.
