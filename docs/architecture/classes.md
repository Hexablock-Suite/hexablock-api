Status: draft for team review, 2026-10-31. Part 1 covers layer 1: the progress entities and the level schema. Part 2 covers layer 2: the use cases and their ports. Part 3 covers layers 3 and 4: the adapters and the drivers.

This page answers statement §4.1 for the API, as decision D6 asks (it replaces assumption A9). It shows the generic types in UML template notation, the layer of each class, and the design patterns. Each view shows at most seven classes and eight relationships. IDs such as A5, D6 and Q10 refer to [`docs/REQUIREMENTS.md`](../REQUIREMENTS.md). DS-4, DS-5 and DS-6 are the data shape decisions of its §4. The layers themselves are in [layers.md](layers.md). The extension points are in [extensibility.md](extensibility.md). ## Whole model in draw.io

[`classes.drawio`](classes.drawio) holds the whole class model in one draw.io file, with 5 pages. Open it in draw.io or diagrams.net.

- Page 1, `All classes`, holds every class, interface and type of the model once, by layer: layer 4 at the top and layer 1 at the bottom, so every dependency points down.
- Pages 2 to 5, `Domain`, `Use cases`, `Adapters` and `Infrastructure`, hold one part each. A part page shows the types of its part in full. A grey box with the name only is a type of another part that one of its lines touches, and its eyebrow names the page that details it.
- A solid box is a type that exists in the code at `284c219`. A dashed box with `«planned»` is design from the views of this page that the code does not have yet. It keeps the `«Sprint N»` of its view when the view gives one.
- `members not designed yet` marks a planned class that no view details.
- A grey line with `planned` in its label is a line of a view that the code does not have yet. The tool finds a use in the members of a type and in the top-level functions of the same file. It does not follow a function that another file exports. So two lines of view `ad-1-progress-store` stay planned, although the code has them: `ProgressRowMapper` → `PlayerProgressReceiver` and `DrizzleProgressRepository` → `ProgressKeyReceiver`. Each class calls a helper of `src/adapters/received.ts`, `receiveProgressOf()` or `receiveProgressKeyOf()`, and that helper gives the receiver to the domain object ([#196](https://github.com/Hexablock-Suite/hexablock-api/issues/196)).
- `«dataType»` marks a class in the code with no operation: it only carries data, by design. An interface with no operation carries `«interface»` alone. `«enumeration»` marks a union of literals, such as `LevelProblem`, with one literal per line. A type alias carries no kind word: its box shows its name and `= <aliased type>`, or its attributes, as `Result` and `ProgressProblem` do. `«module»` marks `AppModule`, a Nest module that only holds decorator metadata. Changed on 2026-11-24: before, `«dataType»` marked every type in the code that only carries data, so 22 interfaces showed `«dataType»` too, a union of literals showed `«union»`, and a type alias showed `«type»` or `«union» «type»` as a stereotype.
- A line of structure (extends, implements, aggregation, composition) is thick. A `use` line is thin and light, and it lives in the draw.io layer `use lines`. Hide that layer in Edit > Layers to read the structure alone.
- Inside a group of 12 boxes or more, a frame holds the boxes of one view of this page. The frame title is the file name of the view in [`classes/views/`](classes/views/), for example `view ad-3-http` for `ad-3-http.png`.
- The pages follow the reading rules of the next section, and each page has a legend.

The file is generated from the code at `284c219` plus the views of this page, by the tool [`drawio-clases`](https://github.com/Hexablock-Suite/.github/tree/main/tools/drawio-clases) of the organization repository. The README of the tool gives the commands. [`classes.config.json`](classes.config.json) maps the folders and the views to layers and parts. [`classes.layout.json`](classes.layout.json) fixes the order of the groups of each band and of the boxes of each group.

A hand edit of that order survives. Move the boxes in draw.io, run `pin.mjs` of the tool to write the order into `classes.layout.json`, and generate the file again. Commit `classes.drawio` and `classes.layout.json` together. Any other hand edit is lost at the next generation: a pixel position, a line route, a text or a style.

## How to read it

- The colored zone is the Clean layer, with the colors of [layers.md](layers.md): yellow for layer 1, purple for layer 2, light blue for layer 3 and dark blue for layer 4.
- One view can show several layers. The zones are bands, with the outer layer at the top and the inner layer at the bottom, so every dependency between layers points down.
- A dashed frame groups the classes of one GoF pattern or one group. Its label names the source, for example `STRATEGY · §3.3 · DS-6`. A frame is not a class. No line starts or ends on a frame. When two classes of different groups depend on each other, the line joins those two classes. A line from one frame to another frame would claim that every class of the first group uses every class of the second group, and that is usually false. The professor asked this about a frame-to-frame arrow in the session of 2026-11-03: «todas esas usan los tres bloques de abajo, a lo mejor la respuesta es no».
- A dashed frame labelled `Aggregate` marks the boundary of one aggregate. It encloses the root and its members: an internal entity, and each value object that the root holds, directly or through another member, such as the `UserId` of a `ProgressKey`. A receiver interface, a port, a use case, a domain service and another aggregate stay outside. Its dashes are longer and darker than the dashes of a pattern or group frame, and its label names the root and the decision that draws the boundary, for example `Aggregate · PlayerProgress · decision 2`. When a class that is not a member sits between the members, the frame turns a corner around it. As with any frame, no line starts or ends on it. Views 1.1, 1.2, 1.3, 1.5 and slice 1 draw one frame each, for `PlayerProgress`, `User` and `LevelDefinition`. Slices 2 and 3 draw the root as a full class with no member, so the frame encloses the root alone, and the footnote names the view of its members. A view that draws a root only as a reference box draws no frame: views 2.3, 3.2 and 3.5. View 1.4 draws `LevelResult`, a member of `PlayerProgress`, without its root, so it draws no frame either.
- The interface of a GoF pattern carries only `«interface»`, and the concrete classes of the pattern carry no role label and no tactical stereotype, as the professor draws them (class of 2026-11-14; design decision of 2026-11-15). The dashed frame of the pattern, or a note, names the pattern. No view shows a role label, such as `«Strategy»`, `«Decorator»` or `«Adapter»`. `«port»` marks an interface that an outer layer implements. `«repository»` marks a repository: the port in layer 2 and its adapter in layer 3. `«port»` and `«repository»` mark a layer, not a role of the pattern, so they also hold inside the frame of a pattern (decided on 2026-11-16 on [#139](https://github.com/Hexablock-Suite/hexablock-api/issues/139)). A domain class carries its tactical stereotype: `«entity»`, `«aggregate root»`, `«value object»` or `«domain service»`.
- An underlined member is static, as in UML.
- The dashed box at the top right of a class holds its type parameters. This is the UML template notation that §4.1 asks for. A full class writes each parameter with its bound, for example `T extends Ordered<T>` and `TSection extends LevelSection`. A dashed class with no members writes the name of the parameter only, for example `TSection`.
- A `«bind»` label on a realization or an inheritance line names the type that each parameter takes, for example `«bind» TSection → FitSection`. A dashed line with an open arrowhead and a `«bind»` label joins a bound class to its template, for example `Range<CharacterCount>` to `Range<T>` in view 1.3.
- The teal class is the focal class of the view.
- A lollipop (a circle on a short line) is the input port that a use case implements.
- A dashed class with no members is a class that another view details. Its eyebrow names that view, for example `PART 2 · VIEW 2`.
- Under the name of a class, an ID such as `API-FR-04` names the requirement it serves.
- A filled diamond (composition) joins the root of an aggregate to each of its internal entities, on the side of the root. An internal entity exists only inside its aggregate, and only the root creates and changes it. The other end names the attribute and its multiplicity, even when it is 1. A hollow diamond (aggregation) joins a decorator to the type that it wraps, on the side of the decorator, with the label `decorate` and the multiplicity `1`. The diamond sits on the class that declares the wrapped attribute. A decorator that inherits that attribute draws no second diamond: `LoggingAspect` extends `UseCaseAspect`, which declares `inner` and carries the diamond to `UseCase`. An aspect is a decorator, so view 2.1 joins `UseCaseAspect` to `UseCase` this way, next to its realization of `UseCase`. Any other attribute is a use arrow with the same role and multiplicity: a value object, the strategy of a context, and a port. For example, `PlayerProgress` keeps its `LevelResult` values, and `LevelDefinition` holds its section, through use arrows. No other hollow diamond appears. This follows the drawings of the classes of 2026-11-13, 2026-11-14 and 2026-11-23 (decision 13).
- A solid line with an open arrowhead is a use: the class depends on the other class. It points from the class that holds or calls to the class it needs. When the other class is an attribute that is not an internal entity, or an attribute across layers, the label names the attribute and its multiplicity. A port counts as across layers: it lives in layer 2, and its adapter lives in layer 3. When the other class is only a parameter, a return value, a local variable or a `new`, the label is a verb. A link that is none of these, such as a guard that a decorator applies or a class that a module only names in its metadata, gets no line; the box or the note names it. This follows the class of 2026-11-02 (decision 13), which replaces the diamond rule of the board of the class of 2026-10-02.
- The legend of each view lists only the line kinds that the view draws.
- The views do not mark which classes are planned. Today `src/` holds the user, progress and level classes of the domain with `Standing` and `LevelsCompleted`, the account and progress use cases with their ports, the `GlobalBoardReader` and `LevelBoardReader` ports with `LeaderboardEntry`, `GetGlobalLeaderboardUseCase`, `GetLevelLeaderboardUseCase`, `AuthController` with `AuthDtoMapper`, `LeaderboardController` with `LeaderboardDtoMapper`, their adapters, the `LevelRepository` port with `DrizzleLevelRepository` and `LevelRowMapper`, the level use cases `GetLevelsUseCase` and `UpdateLevelsUseCase` with `LevelsController`, `LevelDtoMapper` and `LevelDto`, `LevelEditors`, `AuthorizeLevelEditorUseCase` and `LevelEditorGuard` (decision 18), `LoggingAspect` and `AppModule`. `TimingAspect` is planned.

## Part 3: adapters and drivers

Layer 3, `src/adapters/`, and layer 4, `src/infrastructure/`. Adapters never import `src/infrastructure/` (rule `adapters-never-import-infrastructure`). The HTTP adapters and the persistence adapters never import each other (rules `http-adapters-never-import-persistence` and `persistence-adapters-never-import-http`). The persistence adapters never import Nest (rule `persistence-adapters-never-import-nest`). Each folder of layer 3 imports only the library that it adapts: `src/adapters/http` only `@nestjs/*` (rule `http-adapters-import-only-nest`), `src/adapters/persistence` only `drizzle-orm` (rule `persistence-adapters-import-only-drizzle`), `src/adapters/jwt` only `@nestjs/jwt` (rule `jwt-adapters-import-only-nest-jwt`), `src/adapters/logging` only `@nestjs/common` (rule `logging-adapters-import-only-nest-common`), and every other file of `src/adapters` no package (rule `other-adapters-import-no-package`). Among the Node built-ins, `src/adapters/crypto` imports only `node:crypto` (rule `crypto-adapters-import-only-node-crypto`) and `src/adapters/clock` imports none (rule `clock-adapters-import-no-built-in`). Every class that implements a port lives in layer 3, so the adapters of the clock, the logger, token signing, password hashing and the user id generator are there too ([#212](https://github.com/Hexablock-Suite/hexablock-api/issues/212), option C). Layer 4 keeps glue code only, and no file of it except `app.module.ts` imports a port (rule `infrastructure-imports-no-port`). ## Data shapes

The team closed two data shape decisions on 2026-10-30. The app draws the same names on its side.

**DS-5: two tables for progress** (option «B · Dos tablas»). It serves API-FR-02 and API-FR-03.

| Table           | Key                           | Other columns                 | Read by                                   |
| --------------- | ----------------------------- | ----------------------------- | ----------------------------------------- |
| `progress`      | `userId`, `gameId`            | `highScore`, `updatedAt`      | sync, global leaderboard per `gameId`     |
| `level_results` | `userId`, `gameId`, `levelId` | `stars`, `moves`, `elapsedMs` | sync, per-level leaderboard for Fit, Sort |

**DS-6: one level schema, a common part and a typed section** (option «A · Común + sección tipada»). It serves API-FR-04.

| Part         | Fields                                              | Checked by                                                                                        |
| ------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Common       | `gameId`, `levelId`, `order`, `version`, `topology` | `LevelDtoMapper` (shape), then `GameId`, `LevelId`, `LevelOrder`, `LevelVersion` and `TopologyId` |
| Fit section  | `figure`, `pieces`, `witness`, `stars`              | `FitSection` (shape, and A5 on the `Topology` of the level)                                       |
| Sort section | `radius`, `goals`, `source`, `stars`                | `SortSection` (shape)                                                                             |

The Fit `stars` field is a list of `FitStarThreshold`, each one a `maxMoves` count and a `maxElapsedMs` time, and a Fit star needs both ([hexablock-app#60](https://github.com/Hexablock-Suite/hexablock-app/issues/60), 2026-11-06). The Sort `stars` field is a list of `Moves` limits, one `maxMoves` count per star (stars by moves, [hexablock-app#59](https://github.com/Hexablock-Suite/hexablock-app/issues/59), 2026-11-06). In both sections the stars are cumulative: star N needs star N-1. [`docs/level-format.md`](../level-format.md) gives the exact JSON of each field, with one complete example per variant (decision 4).

The API rejects a Fit level that fails A5: the piece areas differ from the figure area (`unequal-area`), or the witness does not place each piece once and cover the figure exactly (`inexact-witness`). `UpdateLevelsUseCase` checks every level before it saves any level.

**DS-4 is closed** (2026-11-06, [#24](https://github.com/Hexablock-Suite/hexablock-api/issues/24)). The best result of a level has more stars; on equal stars, fewer moves; on equal moves, less time. On a full tie, the stored result stays. `LevelResult.isBetterThan()` holds this order: it asks `Stars.isMoreThan()`, then `Moves.isFewerThan()`, then `ElapsedTime.isShorterThan()`. `PlayerProgress.recordLevel()` keeps the best result of each level (DS-12). The same order ranks the per-level leaderboard of Fit and Sort. The global leaderboard of Lines and Merge ranks by `Score.isHigherThan()`. The global leaderboard of Fit and Sort ranks by `Standing.isBetterThan()`: more total stars, then more levels completed, then fewer total moves, then less total time (S3-03, confirmed on 2026-11-16 on [#76](https://github.com/Hexablock-Suite/hexablock-api/issues/76)). `GlobalBoardReader` and `LevelBoardReader` only filter and sum, and `RankedBoard` orders the entries with these comparisons and gives each row its rank; the use case holds the board that the domain builds, and the adapter adds no order (decision 2).

## Why each abstraction exists

Every abstraction cites a requirement, a declared variation or a layer boundary. A class with no citation stays a plain class.

| Abstraction                                    | Reason                                                                                                                   |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `UseCase<TRequest, TResponse>` and input ports | Layer boundary: the controllers depend on the interface (layers.md). One aspect wraps any use case (§3.5).               |
| Output ports (`ProgressRepository` and others) | Layer boundary (§3.4, Q10). The database engine row of §8.                                                               |
| `PasswordHasher`, `TokenIssuer`, `Clock`       | Layer boundary: the use cases do not read the system clock or a crypto library (API-NFR-11, rule R-deterministic-core).  |
| `Result<T, E>`                                 | A use case returns an expected failure as a value. No exception crosses the input port to the HTTP layer.                |
| `LevelDefinition<TSection>`                    | DS-6: one schema with a typed section per `gameId`. Generics are required (D6).                                          |
| `LevelValidator<TSection>`                     | DS-6: each variant picks its own section type. The section checks its shape and holds its rules, A5 for Fit (API-FR-04). |
| `Topology` and `Topologies`                    | D4, §8: a square, triangular or 3D topology. A5 asks the `Topology` of a level for its cells and steps (decision 6).     |
| `Range<T>`                                     | Credential limits (#60): one `Range<CharacterCount>` each for `Username`, `Password` and the HTTP adapter (D6, #99).     |

Plain classes: the row mappers, the HTTP mappers, the controllers, `LevelDto`, the guard and the filter. `LeaderboardEntry<TResult>` is a response type of layer 2 in `src/application/ports/`, with no tactical stereotype. It holds the `UserId` of the player, the `Username` of the account of the player and the domain value that ranks the player: a `LevelResult`, a `Score` or a `Standing`. The `Username` lets a client show a name on the board: Oscar chose option A on 2026-11-27 on [hexablock-app#47](https://github.com/Hexablock-Suite/hexablock-app/issues/47), and [#230](https://github.com/Hexablock-Suite/hexablock-api/issues/230) built it. The entry carries the value object, not a text, and `RankedBoard` delivers it to its `RankedBoardReceiver` beside the `UserId`; the order still reads only the result and the `UserId`. `DrizzleLeaderboardReader` joins the `users` table for the name, so it reads one table of the user module. It has no rule of its own, because the order of each board lives in that value object of the domain (decision 2). It is an alias of `BoardEntry<T>`, which `src/domain/progress/ranked-board.ts` exports as the entry that `RankedBoard.of()` takes, so the shape has one declaration ([#213](https://github.com/Hexablock-Suite/hexablock-api/issues/213)). `BoardEntry` is a type alias with no rule, as `Result` is, and the alias adds no bound on `TResult`. `PlayerProgressReceiver` and `UserReceiver` are receiver interfaces of the domain with no tactical stereotype: each aggregate delivers its parts to one of them, as a value object delivers its datum, and only the border implements them (decisions 2, 15 and 16). `ProgressKeyReceiver` is the same kind of interface for the two parts of a `ProgressKey`. Through them each aggregate gives its state to the border, as the Memento of decision 2 asks. `ProgressKeyValues`, `ProgressValues` and `UserValues` in `src/adapters/received.ts` hold the plain values that the border receives; they are types of the border, not of the domain. `LevelValidators` is not a plain class: it is a «domain service» that picks the strategy of an incoming level by its `gameId`, outside any level, and keeps no state that changes (decision 5). The composition root fills it, so it needs no interface of its own.

## Domain design rules

These rules say how the domain model must be. They apply to every class of `src/domain/`, built or planned, and to the class views that draw it. They come from the classes of 2026-11-13 and 2026-11-14 and from the design decisions of the team of 2026-11-15. When the code does not follow a rule yet, the code changes, not the rule. Rule R-domain-design of `AGENTS.md` points to this section.

### Aggregates

- **The root is the only door.** Code outside an aggregate sends every message to its root. No public method of the root returns an internal entity or another aggregate. Only data in domain types leaves the aggregate, never a part that the caller can change (classes of 2026-11-13 and 2026-11-14).
- **Invariants hold after each operation.** When an operation on the aggregate ends, every invariant of the aggregate holds. The boundary of the aggregate encloses the true invariants of the business (class of 2026-11-13).
- **Global identity only in the root.** The system identifies the root of an aggregate in one universal way. An internal entity has a local identity: it has a meaning only inside its aggregate (class of 2026-11-13). The factory of the aggregate builds that local id from the identity of the root, and it asks no id generator for it (design decision of 2026-11-15).
- **One repository per aggregate.** Each aggregate has its repository in the design, also when its adapter keeps the data in memory. The port carries the name of the aggregate, and it saves and finds the whole root with its parts. No repository exists for an internal entity or for another part of an aggregate (classes of 2026-11-13 and 2026-11-14).
- **One aggregate per transaction.** A transaction changes one aggregate. A use case can read many aggregates, but each transaction changes only one of them. Outside the boundary of an aggregate, the system accepts eventual consistency. If one operation must change two aggregates at the same time, the boundary is wrong (classes of 2026-11-13 and 2026-11-14). When one request changes several aggregates, the use case checks all of them first. Then it saves each aggregate in its own transaction (design decision of 2026-11-15).
- **Reference by identity.** An aggregate refers to another aggregate only by the identity that the system gives to the other root. It never holds the other aggregate, and it never refers to it by a business key that can change, such as a username. If an aggregate needs data of another aggregate, it keeps a local view with only that data. That view can be out of date for a short time (class of 2026-11-13).
- **Events, not questions.** An aggregate never asks another aggregate for data. It tells its changes through domain events, and each listener reacts. The root only records its events. A use case delivers them after the change (class of 2026-11-13; design decision of 2026-11-15).
- **Small aggregates.** An aggregate holds the true invariants of the business and no more, so it stays small. A value object is never the root of an aggregate. Two concepts that the business defines separately never share one aggregate (class of 2026-11-13).

### Domain services

- A domain service is a business operation of the domain layer that does not belong to an entity, a value object or an aggregate (class of 2026-11-13).
- First, try to put the operation in an aggregate. The operation does not go there if it must load other aggregates or create objects of another aggregate. It is a domain service only when no aggregate can hold it (class of 2026-11-13).
- A domain service has no state. It has one public method, which takes and returns domain objects. Private methods can help it (class of 2026-11-13).
- Its name and the name of its method use verbs of the language of the game. A name such as `ProgressHelper` or `LevelManager` is wrong (class of 2026-11-13).
- It receives entities and value objects that are already loaded, applies the rule and returns a result. It never calls a repository, it opens no transaction, and it never touches the infrastructure (classes of 2026-11-13 and 2026-11-14).
- The rules of each aggregate stay inside the aggregate. A domain service only coordinates what no aggregate can do alone (class of 2026-11-13).
- A use case is an application service, not a domain service. It loads the aggregates through their repositories, asks the domain, and saves the one aggregate that changed (classes of 2026-11-13 and 2026-11-14).

### Values, time, orders and names

- **Value objects are immutable.** A value object keeps each field private and `readonly`, it has no setter, and an operation that gives a different value returns a new value object (class of 2026-11-14).
- **One failure mechanism.** The factory of every value object returns a `Result`: a datum that breaks the rule gives a failed `Result`, never an exception (design decision of 2026-11-15). A factory that no datum can fail returns the value itself, and a factory that a datum can fail keeps returning a `Result` (decided on 2026-11-16 on [#139](https://github.com/Hexablock-Suite/hexablock-api/issues/139)). `LevelResult.of()` and `ProgressKey.of()` return the value itself (decisions 2 and 3, [#148](https://github.com/Hexablock-Suite/hexablock-api/issues/148)). The failure carries a code for the broken rule, and the border writes the message. For a level problem, the code is the message (decision 11). Only a guard against a programming defect, such as a missing argument, can still throw. This is the mechanism of decision 11.
- **The border builds the domain values.** An adapter of layer 3, such as a DTO mapper, builds the domain values from the request. A use case receives domain values, and it never builds a domain value from a loose primitive (design decision of 2026-11-15). This extends decision 12 to every use case.
- **Time is a value object.** The domain model holds no `Date`: no field, parameter or return value in `src/domain/` is a `Date` (class of 2026-11-14). The value object of a time takes its name from the language of the game, for example the instant of a sync. Each time concept with a different meaning has its own value object. A general name, such as `Instant`, is correct only when the domain has one meaning of time (design decision of 2026-11-15). Today the domain has one time concept, the instant of a sync, and its value object is `SyncInstant` (decision 3).
- **Each ranking order lives in the domain.** An order that ranks domain objects, such as the order of a leaderboard, lives in one value object of the domain, which compares two of them. A reader port only filters and sums. `RankedBoard` ranks the board in the domain: it sorts the entries with the comparison of the value object of the board and gives each row its rank, so a full tie shares a rank (decision of #83). The use case holds the board that the domain builds and orders nothing, and the adapter adds no order (design decision of 2026-11-15). This applies the rule of decision 2 to every ranking: the rules stay in the domain, and the adapter adds none.
- **Names from the language of the game.** A domain class and its public operations take their names from the language of the game, not from a technique or a pattern. A technical name is correct only for a technical device, such as the receiver interface of decision 15 (classes of 2026-11-09 and 2026-11-13).

## Business rules

Each business rule of [`docs/REQUIREMENTS.md`](../REQUIREMENTS.md) has a type, an owner and a home in the code ([#178](https://github.com/Hexablock-Suite/hexablock-api/issues/178), from the class of 2026-11-23). The type follows one test: could the rule hold on paper, with no computer? If yes, it is an enterprise rule. If it names a technology, such as a column, a token, an HTTP code or a log, it is an application rule.

- **Enterprise rule.** The rule holds on paper, with no software. It lives in the domain, layer 1.
- **Application rule.** The rule exists only because the API runs it. It lives in a use case, layer 2, or at the border, layers 3 and 4.
- **Mixed rule.** The rule has an enterprise half and an application half. Each half lives in its own layer.
- **Integrity rule.** The database keeps a key or a unique index as a backstop of a rule of the domain.
- **Defined by** names who sets the rule, with its requirement ID of `docs/REQUIREMENTS.md`, its section of the statement or the issue that decided it.
- **Lives today** follows the code of 2026-11-26: the class that owns the rule, with a link to its file, and its layer. When a rule does not live in its place yet, **Must live** names the open issue that moves it or builds it.
- API-FR-05, the API-NFR requirements, A7 and A9 say how the API is built, checked, documented and published. They are not business rules, so the table has no row for them.

## Decisions to check with the team

1. **Ports in the application layer.** The class of 2026-10-30 answered Q10: the ports belong to the application layer. Every port in this diagram is in `src/application/`, and the code has `Clock` in `src/application/ports/clock.ts`. Domain code never imports a port: a method such as `recordScore(score, at)` takes the instant as a parameter. One kind of interface lives in the domain: when the domain needs something that the infrastructure gives, the domain declares the interface and the infrastructure implements it (class of 2026-11-13). That is dependency inversion, so the dependency rule holds. `PasswordVerifier` is such an interface (decision 16).
2. **One progress aggregate over two tables (DS-5).** The domain comes first: `PlayerProgress` is the aggregate root, one per `userId` and `gameId`. Its identity is the `ProgressKey` value object ([#107](https://github.com/Hexablock-Suite/hexablock-api/issues/107)): it holds the `UserId` and the `GameId` in private fields, `equals()` compares both, and `deliverTo(receiver: ProgressKeyReceiver)` gives both to a receiver of the border in one call. `ProgressKey.of(userId, gameId)` takes the two value objects built and returns the key itself (rule «One failure mechanism», [#148](https://github.com/Hexablock-Suite/hexablock-api/issues/148)). Each one guards its own rule, and any user can have a progress in any game, so no pair of valid parts breaks a rule, and the factory has no failure to give. `SyncProgressUseCase`, `GetProgressUseCase` and `ProgressRowMapper` use the key that it returns. The day a rule joins a user and a game, `ProgressKey.of()` becomes a `Result` factory with its own failure code. An argument of another type is a defect of the caller, so its guard throws a `TypeError`. `PlayerProgress` holds one `ProgressKey`, and `PlayerProgress.equals()` compares the two keys. The name `ProgressKey` is provisional until the team reviews it. Views 1.1, 2.2 and 3.1, slice 1 and the sync progress sequence of [flows.md](flows.md) draw the key and the port signatures. It keeps its `LevelResult` values and is the only way to record one, so `LevelResult` has no repository and no `userId` or `gameId` of its own. `LevelResult` has no public field either: its four value objects are private, `LevelResult.of()` takes them built, and `LevelResult.deliverTo()` gives them to a receiver of the border (decision 3). `ProgressRepository` reads the whole aggregate with `find(key)` and changes it with `update(key, change)`: both take the `ProgressKey`, which the use case builds from the `userId` and the `gameId` of its request. `update()` holds a lock for the key, passes the stored aggregate or `null` to the change, and saves the whole aggregate that the change returns. So two overlapping syncs of one key run one after the other. The rules, such as the highest score, stay in the domain; the adapter adds none. `DrizzleProgressRepository` splits it into the two tables of DS-5: `progress` keeps one row per `userId` and `gameId`, and `level_results` keeps `userId`, `gameId`, `levelId`, `stars`, `moves` and `elapsedMs`. The aggregate keeps only the best result of each level (DS-12) by the order of DS-4: `recordLevel()` keeps a new result only when `LevelResult.isBetterThan()` ranks it above the stored one. The aggregate has no getter, no public field and no snapshot type (design decisions of 2026-11-09 and 2026-11-15). `PlayerProgress.deliverTo(receiver: PlayerProgressReceiver)` gives its parts to a receiver of the border in one call, as a value object delivers its datum (decision 15): the `ProgressKey`, the `Score` or `null`, the `SyncInstant` of `updatedAt` and a new list of the `LevelResult` values. The values are immutable and the list is new, so a change to what the receiver gets does not change the aggregate. `ProgressRowMapper` and `ProgressDtoMapper` receive the parts through `receiveProgressOf()` of `src/adapters/received.ts`, which also receives the `userId` and the `gameId` of the key through `receiveProgressKeyOf()`, receives the four values of each `LevelResult` and builds a `Date` from the milliseconds that the `SyncInstant` delivers. `DrizzleProgressRepository` builds its lock key `<userId>:<gameId>` and its SQL filters from `receiveProgressKeyOf()`, so the lock key text and the SQL are the same as before the key, and the in-memory repository of the tests builds its map key the same way. `PlayerProgress.restore(key, highScore, updatedAt, results)` builds the aggregate again from the delivered parts, in the order of the receiver: it checks the key and the instant as `start()` does, and it records the high score and the results with the rules of `recordScore()` and `recordLevel()` at the stored instant, so `updatedAt` stays the stored instant ([#97](https://github.com/Hexablock-Suite/hexablock-api/issues/97)). No type parameter stands for the instant, and no `Date` enters the domain (decision 3). This is the Memento of Millett and Tune: the aggregate hides its state and delivers it to the border, and the repository maps it to the data model (views 1.1, 3.1 and 3.5). The aggregate keeps its results in a list and finds the stored result of a level with `LevelResult.isForSameLevelAs()`, which compares two `LevelId` values with `equals()`. It keeps no map with a text key taken out of the `LevelId` (design decision of 2026-11-09); a game has few levels, so the list is enough. The order of the leaderboards lives in the domain too (design decision of 2026-11-15, section «Domain design rules»): `LevelResult.isBetterThan()` ranks the board of a level (DS-4), `Score.isHigherThan()` ranks the global board of Lines and Merge, and `Standing.isBetterThan()` ranks the global board of Fit and Sort (S3-03). `GlobalBoardReader` and `LevelBoardReader` only filter and sum. `DrizzleLeaderboardReader` implements both: it reads the `progress` and `level_results` tables, filters by `gameId` and by level, sums the totals of each player, and adds no order; it names no table or column of the user module. `GetGlobalLeaderboardUseCase` and `GetLevelLeaderboardUseCase` order the entries with the comparisons of the domain. Two names come from the words of S3-03. The value object for «levels completed» is `LevelsCompleted`: it counts the stored results of a player in one game, so a level counts once (DS-12). A row of a global board is a `LeaderboardEntry<Score>` for Lines and Merge and a `LeaderboardEntry<Standing>` for Fit and Sort: one generic entry serves the three boards, and its type argument is the domain value that ranks the row, so no row carries a nullable field of another board. `Standing` holds four totals: a `Stars`, a `LevelsCompleted`, a `Moves` and an `ElapsedTime`. A board lists only the players that have something to rank: a stored result of the level, a high score, or at least one completed level, because `Standing.of()` fails with `no-level-completed`. The entry names the player by its `UserId`. A later player name is an added field, filled through a port of the user module.
3. **The progress row fields (proposal).** DS-5 fixes the key. `highScore` and `updatedAt` are our proposal: the app keeps a high score for Lines and Merge, and the use case reads the instant from the Clock port and passes it to the domain. `updatedAt` is the instant of the last sync of the progress, and its value object is `SyncInstant`, a name from the language of the game (design decision of 2026-11-15; built, [#97](https://github.com/Hexablock-Suite/hexablock-api/issues/97)). `SyncInstant.of()` takes the milliseconds since the Unix epoch and guards the rule of a valid instant: a whole number of milliseconds inside the range of a JavaScript `Date`. A number that breaks it gives a failed `Result` with the code `invalid-sync-instant`. `SyncInstant.isLaterThan()` compares two instants. The `Clock` port gives a `SyncInstant`, which `SystemClock` builds, and `SyncProgressUseCase` passes it to `start()`, `recordScore(score, at)` and `recordLevel(result, at)`, so the use case checks no instant. Each record moves `updatedAt` to the instant of its sync, and the aggregate keeps `updatedAt` from moving back: a record with an earlier instant leaves it, and a sync that records nothing leaves it too. `PlayerProgress` keeps the `SyncInstant` in a private field, so no field, parameter or return value of the progress is a `Date` or a number of milliseconds. The `updated_at` column keeps a timestamp, and the JSON bodies keep the same ISO 8601 text as before: `receiveProgressOf()` builds the `Date` of the row and of the body, and `ProgressRowMapper` builds the `SyncInstant` of a stored row; a stored instant that breaks the rule, such as `infinity`, is a server fault (decision 11). In the domain the high score is a `Score` value object, not a number (design decision of 2026-11-09: no primitive crosses a public signature of the domain model, the boolean and the delivery of decision 15 excepted). `Score.of()` guards the rule: a score is a non-negative safe integer, and a number that breaks it gives a failed `Result` with the code `invalid-score` (decision 11). `Score.isHigherThan()` tells which of two scores wins, and `PlayerProgress.recordScore()` keeps the higher one. A progress with no score yet holds `null`, so it differs from a score of 0. The `high_score` column and the JSON bodies keep a number: only `ProgressRowMapper` and `ProgressDtoMapper` receive the number of a `Score` (decision 15), and `ProgressDtoMapper` builds the `Score` of a sync from the body. The same decision holds for a level result (view 1.4): `LevelResult` holds a `LevelId`, a `Stars`, a `Moves` and an `ElapsedTime` value object, not a string and three numbers. `LevelId.of()` guards a non-blank text. `Stars.of()`, `Moves.of()` and `ElapsedTime.ofMs()` each guard a non-negative safe integer, and `ElapsedTime` counts milliseconds. Each factory returns a `Result` with the code of its rule: `invalid-level-id`, `invalid-stars`, `invalid-moves` or `invalid-elapsed-time`. Each one compares by value with `equals()`. The `level_results` columns and the JSON bodies keep text and numbers, so only the border builds and receives these value objects ([#95](https://github.com/Hexablock-Suite/hexablock-api/issues/95)). `LevelResult` keeps the four in private fields and has no getter. `LevelResult.of(levelId, stars, moves, elapsedTime)` takes the four value objects and checks nothing more, so it takes no raw value, cannot fail and returns the `LevelResult` itself. `ProgressDtoMapper` builds the four from the body, and `ProgressRowMapper` and `DrizzleLeaderboardReader` build them from a `level_results` row. All three call `buildLevelResult()` of `src/adapters/built.ts`, which combines the four `Result` values in the order of the fields and gives the first failure ([#103](https://github.com/Hexablock-Suite/hexablock-api/issues/103)). `LevelResult.deliverTo(receiver: LevelResultReceiver)` gives the four value objects to a receiver of the border in one call, as `Standing.deliverTo()` gives its four totals. The helper `receiveLevelResultOf()` of `src/adapters/received.ts` receives them as `LevelResultValues`, the text and the three numbers of a row or a body; that type lives in the border, not in the domain. The four names are provisional until the team reviews them with the app.
4. **One generic level type, born valid (DS-6, S3-02; built, [#77](https://github.com/Hexablock-Suite/hexablock-api/issues/77)).** `LevelDefinition<TSection extends LevelSection = LevelSection>` holds the common part of DS-6 (`gameId`, `levelId`, `order`, `version` and `topology`) and a section, and `TSection` is `FitSection` or `SortSection`. The class carries the bound, not only its factory `of()` ([#222](https://github.com/Hexablock-Suite/hexablock-api/issues/222), option D). The class holds the section in a field of type `TSection` and asks it `mostStars()`, so the bound belongs where the field is, as `Range<T extends Ordered<T>>` carries its bound on the class (decision 17). Before #222 only `of()` carried the bound, and the field had the type `TSection & LevelSection` to make up for it. Statement §3.1 asks for a bound where the code needs a capability of the content, and §6.1 asks the README to explain each parameter and its bound. A level is born valid: `LevelDefinition.of()` takes the values of the common part and the `Result` of the section factory, and it returns a `Result`. Each section checks its own shape when it is created (`FitSection.of()`, `SortSection.of()`), so no level with an unchecked section exists in the domain, and `AnyLevel` is gone. The unchecked JSON stays in `LevelDto`, in layer 3. A level of any game has the type `LevelDefinition`, which takes the default `LevelSection`: each section is valid, and only the strategy of its game knows its type. The default only keeps the callers short, so no caller writes `LevelDefinition<unknown>`, which the bound rejects. Views 1.2 and 1.5, slice 3 and views 1 and 2 of [extensibility.md](extensibility.md) write the bound in the template box of `LevelDefinition` and of `LevelValidator`. `LevelDefinition` is an «entity» and the «aggregate root» of one level. Its identity is the `gameId` plus the `levelId`, and it has its own repository, `LevelRepository` (built, [#80](https://github.com/Hexablock-Suite/hexablock-api/issues/80)). The section is a value object, so it has no repository. Why one level is the boundary: the section rules hold inside one level (its shape now, and A5 for Fit with #79), and the version rule of S3-10 compares two copies of the same level, the stored copy and the incoming copy. No requirement links two levels: DS-6 defines one level, DS-11 compares two copies of one level, S3-02 fixes the format of one level, and S3-10 rejects a lower `version` of one level. So a bigger aggregate, such as every level of a game, would enclose no true invariant, and a smaller one would split the version rule from the level that it protects. The version rule lives in the root (#80): `stored.accepts(incoming)` returns a `Result`. It rejects a copy with a lower `version` with the level problem `older-version`, and it gives the incoming copy for an equal or a higher `version`, so a retry of the same update is safe. A copy of another level is a defect of the caller, so `accepts()` throws. Since [#174](https://github.com/Hexablock-Suite/hexablock-api/issues/174), `decideReplace(stored)`, called on the incoming copy, decides over the stored state: an absent store takes it, a valid stored level decides through `accepts()`, and a broken row compares only its stored version, when the row holds one (decision 19). `UpdateLevelsUseCase` only coordinates: its change is `level.decideReplace(stored)`, so it holds no branch on the stored state. `isIdentifiedBy(gameId, levelId)` tells if a level has that key. `LevelRepository.update(gameId, levelId, change)` holds an advisory lock for the `gameId` and the `levelId`, passes the stored state of the level to the change (absent, valid, or broken for a row that breaks a rule, [#147](https://github.com/Hexablock-Suite/hexablock-api/issues/147)), and saves the level that a successful change returns, one level per transaction, as `ProgressRepository.update()` does (decision 2). The change runs `accepts()` again under that lock, so an update that races another one cannot save an older level, and the adapter adds no rule. A change that returns a level with another key saves nothing, because the lock covers only its own key. `list()` gives every stored row by `gameId` and then by `levelId`: the valid levels and the broken rows apart (decision 19). The level has no getter: `deliverTo()` gives its common part and its section to a receiver of the border (decision 6). `UpdateLevelsUseCase` checks every level first and then saves each level in its own transaction (section «Domain design rules»). The shared level format is [`docs/level-format.md`](../level-format.md): the fields and their rules, one complete Fit example and one complete Sort example. The app writes its level files in it (hexablock-app#166 and #167), and the level tests of #77, #78 and #79 read their fixtures from it. It codes S3-02 of [#76](https://github.com/Hexablock-Suite/hexablock-api/issues/76), confirmed on 2026-11-16. Lines and Merge have no level files (API-FR-04). View 1.2 draws the level and its strategies, and view 1.5 draws its values.
5. **`LevelValidators`, a domain service that picks the strategy by `gameId` (built, #77).** `LevelValidator<TSection>` stays the Strategy of each variant with level files (§3.3, DS-6), but it holds no rule. The section checks its own shape and holds its own rules, so `isSection()` is gone. The strategy only picks the section type: `sectionOf(raw, topology)` asks its section type to read the section as it arrives, and it passes the topology to the rules that need it, such as A5 (decision 6). `SortLevelValidator` implements it for Sort (built, [#78](https://github.com/Hexablock-Suite/hexablock-api/issues/78)): `sectionOf()` returns what `SortSection.of()` gives, and it does not pass the topology on, because no rule of the Sort section needs it. `SortSection` holds the rules of the Sort section: exactly its four fields, a radius and a goal of 1 or more, one of the two kinds of source, and one star threshold or more, each one a `Moves` limit. So a negative threshold gives the level problem `invalid-stars`, never a thrown error. `FitLevelValidator` implements it for Fit (built, [#79](https://github.com/Hexablock-Suite/hexablock-api/issues/79)): it holds `Topologies`, finds the `Topology` of the level and returns what `FitSection.of(raw, topology)` gives (decision 6). `LevelValidators` keeps a small list of entries, one `GameId` and its strategy for each variant with level files, and it finds the strategy of a `gameId` with `GameId.equals()`. It keeps no `Map`: a JavaScript `Map` compares object keys by reference, so two equal `GameId` values would be two keys, and decision 2 rejects a map keyed by a value taken out of a value object. The composition root builds it once with `LevelValidators.of(entries)`. Two entries for one game are a defect of the composition root, so the factory throws. `check()` takes the values of the common part and the section as it arrives, asks the strategy for the section, and builds the level with `LevelDefinition.of()`. A `gameId` with no entry has no level files, so `check()` returns the level problem `game-without-levels`. Why a «domain service»: it picks the strategy from the `gameId` of an incoming level, before and outside any `LevelDefinition`, so no aggregate can hold this choice. It keeps no state that changes: its entries are fixed when the composition root builds it (class of 2026-11-13, section «Domain design rules»). `LevelDtoMapper` builds the values of the common part and passes the section as it arrives. A mapper never picks a section type. `LevelRowMapper` restores a stored row the same way (built, #80): it builds the values of the common part from the row and passes the stored section to `LevelValidators.check()`, so the strategy of the row's `gameId` builds the section. No unchecked section enters the domain, also from the database. A row that no strategy accepts is a broken row, not a level: `toStoredLevel()` gives the code of its first broken rule and its stored version, or no version when the version column breaks the rule of `LevelVersion` (decision 19). The mapper reads the `gameId` of a row only to build the `GameId` that `check()` takes, and it names no section type, so a new variant changes no mapper. `GameId` is an open value object, not a closed list. So a new variant with level files adds a section type, a strategy, one entry in the composition root and one section DTO in `src/adapters/http/level.dto.ts` (issue [#189](https://github.com/Hexablock-Suite/hexablock-api/issues/189)). The section DTO is a change of the HTTP adapter. The core does not change.
6. **Coordinates as value objects, rotation from the topology (built, #77 and #79).** A coordinate is a `Coordinate` value object: a list of one safe integer or more, not a tuple of numbers. The `topology` of the level, a `TopologyId`, says how to read it: the hex topology reads `[q, r]` as axial coordinates. `TopologyId` is an open lowercase slug, so a square, triangular or 3D level (§8, D4) needs no new schema, and the API never rejects a level only because its topology is not hexagonal. The A5 check rotates pieces, and the rotation steps come from the topology: a `Rotation` counts steps, never degrees, and the hex topology has six steps of 60°. `Topology` is an interface of the domain with three rules: `holds(cell)` tells if a `Coordinate` is a cell of the topology, `turn(cell, rotation)` turns a cell around the origin, and `move(cell, at)` moves a cell by the offset of a placement. `HexTopology` implements it with no state: a hex cell has two values, one step turns `[q, r]` to `[-r, q + r]`, and a move adds the offset, as [`docs/level-format.md`](../level-format.md) says. Since [#229](https://github.com/Hexablock-Suite/hexablock-api/issues/229), `SquareTopology` and `TriangleTopology` implement it too, with the rules of the app: a square step turns `[col, row]` to `[-row, col]` and four steps make a full turn; a triangle step turns a cell a sixth of a turn around the vertex at the origin and flips its orientation, and six steps make a full turn. A triangle offset counts lattice cells, so a move takes `[col, row]` to `[col + 2·at.col + at.row, row + at.row]` and keeps the orientation of the cell; a plain sum would flip it. That is why `move()` joined the interface and `FitPiece.coveredCells()` asks the topology for the move. A rotation turns only the steps left after its whole turns, so a negative count turns the other way and a large count runs no long loop; `Rotation.turn()` serves the triangle step as it serves the hex step. `Coordinate.turnedBy()`, `Coordinate.movedBy()`, `Coordinate.hasEvenSum()` and `Coordinate.halved()` do the arithmetic of the cells, so no code outside `Coordinate` reads its values: the triangle step is `turnedBy()`, then `movedBy()` with a shift that `hasEvenSum()` picks, then `halved()`. `Topologies` is the small collection of the known topologies: one entry per topology, a `TopologyId` and its `Topology`. It finds a `Topology` with `TopologyId.equals()` and keeps no `Map`, because a JavaScript `Map` compares object keys by reference. It is a «domain service», as `LevelValidators` is (decision 5): the composition root builds it once with `Topologies.of(entries)`, two entries for one topology throw, and it keeps no state that changes. `FitLevelValidator` holds it, finds the `Topology` that the `topology` field names and passes it to `FitSection.of(raw, topology)` (#79). A level whose topology has no entry gives the level problem `unknown-topology`. The cells of `figure`, `pieces` and `witness` are `Coordinate` values, and a cell that the topology does not hold gives `invalid-figure`, `invalid-pieces` or `invalid-witness`. Then `FitSection` checks A5 on the witness and runs no search: the witness places each piece once, the covered cells have the area of the figure, and each covered cell lies in the figure once. A failure gives `inexact-witness` or `unequal-area`, so equal areas alone never pass, and no `FitSection` that fails A5 exists. The other numbers of the common part are value objects too: `order` is a `LevelOrder`, and `version` is a `LevelVersion`, whose `isOlderThan()` serves DS-11 and the version rule of S3-10. The parts of the sections are value objects as well (`FitPiece`, `PieceId`, `Placement`, `FitStarThreshold`, `BoardRadius`, `GoalCount`, `StackSource`, `Seed` and `TileColor`), and the star limits are `Moves` and `ElapsedTime`. The JSON keeps numbers and text at the border. Every class of the level schema is born with private fields, and the factory of each value object returns a `Result`, never an exception (rule «One failure mechanism»). `Moves.of()` and `ElapsedTime.ofMs()` return a failed `Result` too (#103), and the readers of the star limits turn it into the level problem `invalid-star-threshold`: a bad level file gives a level problem, never a server error. Since #80 the level and the composite values of its sections deliver their parts to a receiver of the border, each in the fields that its factory reads: `LevelDefinition.deliverTo()` gives `gameId`, `levelId`, `order`, `version`, `topology` and `section`, `FitSection` gives `figure`, `pieces`, `witness` and `stars`, `SortSection` gives `radius`, `goals`, `source` and `stars`, and `FitPiece`, `Placement`, `FitStarThreshold` and `StackSource` give their own fields. Each part then delivers its own value. `receiveJsonOf()` in `src/adapters/received.ts` runs these deliveries and gives the JSON of the shared level format. So `LevelRowMapper` writes the section column without a section type, and #81 can build the DTO the same way. No operation returns a part, and no delivery runs in the domain.
7. **One generic input port.** Every input port of [layers.md](layers.md) binds `UseCase<TRequest, TResponse>`, for example `SyncProgress`. One aspect class then wraps any use case (§3.5). The app makes the same choice (its decision 9). The cost: an input port cannot add a second method. The three account ports bind it too ([#104](https://github.com/Hexablock-Suite/hexablock-api/issues/104)): `RegisterUser` binds `UseCase<RegisterUserRequest, Result<UserId, RegisterProblem>>`, `Login` binds `UseCase<LoginRequest, Result<SessionToken, LoginProblem>>` and `AuthenticateToken` binds `UseCase<SessionToken, Result<UserId, TokenProblem>>`, so no input port declares an `execute()` of its own. Every problem type is an object with a `kind`: `LoginProblem` is `{ kind: 'invalid-credentials' }`, `TokenProblem` is `{ kind: 'invalid-token' }`, and `RegisterProblem` already had one; since [#105](https://github.com/Hexablock-Suite/hexablock-api/issues/105) it is only `{ kind: 'username-taken' }`, because the request carries values that follow their rules (decision 12). So `LoggingAspect` can wrap every input port. A unit test wraps each account port in it; `AppModule` does not wrap them, and the HTTP answers do not change. `GetLevels` binds it with `TRequest → void` and `TResponse → Result<ListedLevels, never>`: one call gives every valid level and every broken row apart (decision 19), and the read has no expected failure. `UpdateLevels` binds it with `TRequest → UpdateLevelsRequest` and `TResponse → Result<void, InvalidLevels>` (built, [#81](https://github.com/Hexablock-Suite/hexablock-api/issues/81)). `LoggingAspect` asks for a `kind` on the error type, and both error types meet it, so the aspect can wrap both. `AppModule` wraps `UpdateLevels`, as it wraps `SyncProgress`. Two input ports serve the two leaderboard routes ([#218](https://github.com/Hexablock-Suite/hexablock-api/issues/218), option C, decided by Oscar on 2026-11-26). `GetGlobalLeaderboard` binds `UseCase<GameId, Result<GlobalLeaderboard, never>>`: any `gameId` has a global board (decision 5), so the read has no expected failure. `GetLevelLeaderboard` binds `UseCase<LevelBoardQuery, Result<LevelLeaderboard, UnknownLevel>>`: since [#146](https://github.com/Hexablock-Suite/hexablock-api/issues/146) the board of a level has one expected failure, `UnknownLevel` (`{ kind: 'unknown-level' }`), when the definitions do not hold the level (decision 20). `AppModule` wraps both ports in `LoggingAspect`, each under its own name (decision 10), as it wraps `SyncProgress` and `UpdateLevels` (decision recorded on [#83](https://github.com/Hexablock-Suite/hexablock-api/issues/83#issuecomment-6905667403)). Why two ports: before #218, one port `GetLeaderboard` took the union `LeaderboardQuery` and gave the union `Leaderboard`. Its type said that the global board can fail with `unknown-level`, which it cannot, and the use case, the controller and the mapper each narrowed the union with `query.board === 'level'`. The reason for one port, «one aspect wraps any use case», holds for two ports too, because each port binds `UseCase`. The two use cases also read different things: the global board reads `highScores()` and `standings()`, and the board of a level reads `levelResults()` and asks `LevelRepository.holds()`. So the reader port splits too, into `GlobalBoardReader` and `LevelBoardReader`: no class depends on methods that it does not use (statement §3.2, ISP). `DrizzleLeaderboardReader` implements both reader ports, and `AppModule` binds both tokens to one instance. Each reader port has its shared contract suite, and the Drizzle reader runs both. The cost: one more input port, use case, provider and reader port. The HTTP answers and `openapi/openapi.json` do not change. The other option kept one port and wrote here that `UnknownLevel` is part of the answer of the global board too. The request and response types of an input port live next to its use case, not in the file of an output port ([#213](https://github.com/Hexablock-Suite/hexablock-api/issues/213)): `ListedLevels` and `UnavailableLevel` in `src/application/levels/listed-levels.ts`, and `SessionToken` in `src/application/auth/session-token.ts`. `LevelRepository` and `TokenIssuer` import them from there, so the HTTP mappers import no file of `src/application/ports/`.
8. **No Abstract Factory in the API.** The statement asks for Abstract Factory because the pattern holds the variability of the engine. The engine lives in Hexablock-Suite/hexablock-app, and the app builds the pattern there. The API has no engine: for each variant it validates levels, so a variant has one product, its level validator (`FitLevelValidator`, `SortLevelValidator`). A factory per variant would wrap one constructor. To vary one behavior, the right pattern is Strategy, and the API uses it: `LevelValidators` holds one strategy per `gameId` (decision 5). Decision of the product owner on [#140](https://github.com/Hexablock-Suite/hexablock-api/issues/140), 2026-11-23.
9. **Port names in the language of the game.** A port says what the use case asks for, not how the data travels. For example, `GlobalBoardReader`, not a name that says SQL or HTTP. A name that says how the data travels couples the use case to that technology, as the class of 2026-10-30 explained.
10. **Aspects in layer 2, behind a `Logger` port.** In the session of 2026-11-06 the professor answered Q12: the aspects talk to the use case, so they belong in the application layer, built as decorators with one interface common to the use cases, without libraries. `UseCaseAspect` and `LoggingAspect` live in `src/application/aspects/`. `LoggingAspect` writes to the `Logger` port in `src/application/ports/logger.ts`, so `src/application` stays free of Nest. The port takes a typed entry (the use case name, the outcome, and the `kind` of a failure or the name, the string `code` and the stack frames of a thrown error), never a prebuilt `message: string`. A fourth entry, `unavailable-level`, gives the `gameId`, the `levelId` and the reason code of a stored level row that breaks a rule, and `NestLogger` writes it at warn level with each key quoted as JSON (decision 19). `LoggingAspect` writes it too ([#219](https://github.com/Hexablock-Suite/hexablock-api/issues/219)): an optional last argument of the aspect is a function from the value of a success to extra entries without `useCase`. The aspect adds its own name and writes each extra entry inside `safely()`, before the `success` entry, so a failed write changes no answer. `AppModule` gives `unavailableLevelEntries()` of `src/application/levels/` to the aspect of `GetLevels`. So `LoggingAspect` writes every entry of the port, and no use case imports the port: rule `only-aspects-import-logger-port` of `.dependency-cruiser.cjs` lets only `src/application/aspects/` import `ports/logger.ts`. `NestLogger` in `src/adapters/logging/` implements the port and writes the text through the Nest logger under the context `LoggingAspect`. A failure logs only its `kind`, because the rest of a failure can hold values that the client sent. A thrown error never logs its message, for the same reason: the frames leave out the first line of the stack, which repeats the message, and a thrown value that is not an `Error` logs only its type ([#67](https://github.com/Hexablock-Suite/hexablock-api/issues/67)). The class of 2026-11-02 said that the message «no debería estar allí … En la implementación de este señor, en un adaptador secundario». The `useCase` of an entry is the name of the input port that the aspect wraps, with no suffix: `SyncProgress`, `GetLevels`, `UpdateLevels`, `GetGlobalLeaderboard` and `GetLevelLeaderboard`. Before [#218](https://github.com/Hexablock-Suite/hexablock-api/issues/218) both leaderboard routes logged one name, `GetLeaderboard`; now each line names the board that the request read. A port that the aspect wraps later takes its name by the same rule.
11. **Expected failures as values.** A use case never throws a domain error to the HTTP layer. `UpdateLevels` returns `Result<void, InvalidLevels>` (built, #81). `InvalidLevels` is `{ kind: 'invalid-levels', problems }`. Each problem is a `LevelProblemReport`: the `GameId` and the `LevelId` of one level and the `LevelProblem` code of the rule that it breaks, so a client knows which level to fix. A guard runs before the controller reads the body, so an account outside the list learns no level rule and the API saves nothing. Only the infrastructure reads the environment: `readLevelEditors()` in `src/infrastructure/auth/auth-config.ts`, next to `readJwtSecret()`, splits `LEVEL_EDITOR_IDS` at each comma, trims each entry and skips an empty one. An unset or empty variable gives an empty list. An entry that is not a UUID stops the start, as a missing `JWT_SECRET` does. `AppModule` binds `AUTHORIZE_LEVEL_EDITOR` to the use case with that list. The other options: a check inside `UpdateLevelsUseCase` would mix two jobs in one use case and run after the body checks, and a guard that reads the configuration itself would make layer 3 read the environment. View 2.3 draws `LevelEditors` and `AuthorizeLevelEditorUseCase`, view 3.3 draws `LevelEditorGuard`, and view 3.4 lists the binding. View 1.3 does not draw `LevelEditors`: it holds no part of a `User`, so view 2.3 details it next to the use case that holds it. The names `LevelEditors` and `AuthorizeLevelEditor` are provisional until the team reviews them.

19. **A stored level row that breaks a rule (built, [#147](https://github.com/Hexablock-Suite/hexablock-api/issues/147)).** Decided by Oscar on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) («`PUT /v1/levels` can replace the bad row») and on 2026-11-17 on #147 (option C for the read). A `levels` row that no strategy accepts is a broken row, not a level and not a server fault.
    - **The read under the lock tells three states apart.** `LevelChange` takes a `StoredLevel`, a closed union: `absent` (no row), `valid` (the restored `LevelDefinition`) or `broken` (the code of the first broken rule, a `StoredLevelProblem`, and the stored `LevelVersion`, or `null` when the version column breaks the rule of `LevelVersion`). So a broken row never passes as no row. `LevelRowMapper.toStoredLevel()` builds the valid and the broken states; the repository builds `absent`. Since [#174](https://github.com/Hexablock-Suite/hexablock-api/issues/174), `StoredLevel` and `StoredLevelProblem` live in `src/domain/level/stored-level.ts`, so the domain owns the closed union of the stored states; the `LevelRepository` port imports them.
    - **The update replaces the broken row.** The version rule of S3-10 still holds over a broken row when its stored version is valid: the incoming level replaces the row when its version is equal or higher (`LevelDefinition.isOlderThan()` is false), and a lower version saves nothing and gives the level problem `older-version`. An equal version passes, so the same packaged level replaces its broken row. When the stored version itself breaks its rule, there is no version to compare, and any valid version replaces the row. Over a valid stored level, `accepts()` runs as before. `LevelDefinition.decideReplace(stored)`, called on the incoming copy, now runs the whole rule over the three states ([#174](https://github.com/Hexablock-Suite/hexablock-api/issues/174)): `UpdateLevelsUseCase` passes its change as `level.decideReplace(stored)` and holds no branch on the stored state.
    - **The aspect logs the broken rows ([#219](https://github.com/Hexablock-Suite/hexablock-api/issues/219), option B and a gate, decided by Oscar on 2026-11-26).** Until #219, `GetLevelsUseCase` held the `Logger` port and wrote the entry of each broken row itself, and `AppModule` built it with no aspect. Now `AppModule` wraps `GetLevels` in `LoggingAspect` and gives the aspect `unavailableLevelEntries()`, the function of `src/application/levels/` that turns the `ListedLevels` of a success into one entry per broken row. Why: statement §3.5 asks for logging with no logger call in business code, `GetLevelsUseCase` was the only use case that called the logger, and the professor's written solution of 2026-11-14 keeps the logging in the aspect. A broken row is a fact apart from the call, but that is a reason about the content of the entry, not about where the call lives. The other option kept the call in the use case and wrote down why it is not business code: it left two ways to log in one layer. The entries, their order before `success` and the HTTP answer do not change. The rule `only-aspects-import-logger-port` stops the next use case from importing the port (rule R-logger-in-aspects of `AGENTS.md`). The function is the last argument of the aspect and optional, so a later required argument, such as the `Stopwatch` port of [#181](https://github.com/Hexablock-Suite/hexablock-api/issues/181), comes before it.
    - **The read hides no level.** `LevelRepository.list()` gives `ListedLevels`: the valid levels and the broken rows apart, each `UnavailableLevel` with the `gameId` and the `levelId` of its row as text and the reason code. `LoggingAspect` logs one `unavailable-level` entry per broken row through the `Logger` port, with the same three values and no section, before the `success` entry of the call (decision 10). `GetLevelsUseCase` holds no logger. `GET /v1/levels` answers 200: `levels` holds the valid levels, and the optional `unavailable` field of `LevelsDto` names each broken row with its `gameId`, `levelId` and `reason`. The field is absent when no row is broken, so the answer keeps its old shape.

20. **The board of a level that the definitions do not hold answers 404 (built, [#146](https://github.com/Hexablock-Suite/hexablock-api/issues/146)).** Decided by Oscar on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) (question 1, option B, with the API holding every level).
    - **One query on the level port.** `LevelRepository.holds(gameId, levelId)` answers whether a row is stored for the key. A valid row and a broken row (decision 19) both answer true: a broken row is still a level that the definitions hold, so its board exists. The query takes no lock and restores no level. `DrizzleLevelRepository` reads one key column of at most one row; the in-memory fake and the shared contract pin the same answers.
    - **A named failure of the use case.** `GetLevelLeaderboardUseCase` holds `LevelRepository` next to `LevelBoardReader`. It asks `holds()` first and returns the failed `Result` `UnknownLevel` (`{ kind: 'unknown-level' }`) with no read of the results. `UnknownLevel` is part of the answer of the board of a level only ([#218](https://github.com/Hexablock-Suite/hexablock-api/issues/218)): `GetGlobalLeaderboardUseCase` holds no `LevelRepository`, and its error type is `never`, because any `gameId` keeps its global board (decision 5). `LoggingAspect` logs the kind of the failure.
    - **The border answers 404.** `LeaderboardController` turns `unknown-level` into a `NotFoundException` with the message `No level <levelId> for gameId <gameId>`, and `HttpErrorFilter` answers it with `ErrorDto` (API-FR-06). `openapi/openapi.json` lists the 404 of the level route.
    - **The bundled levels.** The API holds every level, the levels that the app bundles too. Since [#158](https://github.com/Hexablock-Suite/hexablock-api/issues/158), the person who deploys runs the command `pnpm levels:load` of hexablock-app against the new API before traffic reaches it, as the section «Deploy» of the [README](../../README.md#deploy) says. Until the load runs, the board of a bundled level that the API does not store answers 404.

    Views 2.2, 2.3, 3.2 and slice 3 draw `holds()`; view 2.2 draws the use arrow `levels 1` from `GetLevelLeaderboardUseCase` to `LevelRepository`.

21. **Incoming bounds of the progress values, and stored rows that keep their values (built, [#135](https://github.com/Hexablock-Suite/hexablock-api/issues/135); moved to the border by [#179](https://github.com/Hexablock-Suite/hexablock-api/issues/179)).** A value that a client sends must fit its column, so it stops at the border with 400 and the code of its rule, not with a 500 of the database. The bounds exist only because of the Postgres columns, so they are not business rules of the domain: [#179](https://github.com/Hexablock-Suite/hexablock-api/issues/179) moved them out of `GameId`, `LevelId`, `Stars` and `Moves`. The domain keeps only `of()` with the business rule of each value; `ofIncoming()`, `INCOMING_ID_LENGTH`, `MOST_STARS_OF_ONE_PLAY`, `MOST_MOVES_OF_ONE_PLAY` and the control-character helper are gone from `src/domain`.
    - **The border holds the bounds.** `progress-values.ts` in `src/adapters/http/` holds them: `INCOMING_ID_BOUNDS` (1 to 64 characters), `MOST_STARS` and `MOST_MOVES` (2147483647, the largest value of the Postgres `integer` columns `level_results.stars` and `level_results.moves`). The columns are Postgres `text` and give no length, so 64 is a choice of the API. Each builder runs the factory of the domain first, `of()`, which keeps only the business rule, and then checks the bound of the column: `gameIdFrom()` and `levelIdFrom()` count 1 to 64 characters over code points, and `starsFrom()` and `movesFrom()` take at most 2147483647. `levelIdFrom()` also rejects a control character (U+0000 to U+001F, U+007F): by decision of #179 this is a rule of the border, not of the domain, because Postgres rejects a NUL in a text column and the check guards the write; the `GameId` pattern already allows none. The codes stay `invalid-game-id`, `invalid-level-id`, `invalid-stars` and `invalid-moves`.
    - **The time takes the same largest value ([#167](https://github.com/Hexablock-Suite/hexablock-api/issues/167)).** `MOST_ELAPSED_MS` (2147483647, the same largest value as `MOST_STARS` and `MOST_MOVES`) bounds the `elapsedMs` that a client sends. The column `level_results.elapsed_ms` is a Postgres `bigint` and sets no such bound, so the limit is a choice of the API: the sum of the times of one player stays a safe integer for any realistic number of levels, which the standings of the global board sum. `elapsedTimeFrom()` checks it in `progress-values.ts`, the last builder of the order of the fields, and `openapi/openapi.json` publishes it as the `maximum` of `elapsedMs`.
    - **Why the bound is not in `of()`.** `Stars.of()` and `Moves.of()` also build a total: `DrizzleLeaderboardReader` sums the stored rows into a `Standing`, and a sum can exceed one column. `Moves.of()` also builds the move limit of a star threshold, which lives in a JSON column. A bound in `of()` would make a large total fail on read, a 500 of the global board. So the bound lives at the border, where only the values that a client sends pass.
    - **A stored row keeps its values.** The bounds apply where a value comes in, not where a stored row is rebuilt. `ProgressRowMapper`, `DrizzleLeaderboardReader` and `LevelRowMapper` build with `of()`, which holds no incoming bound, so a row stored before the bounds still reads, for example a `levelId` of 10 000 characters. No stored data changes, and no task cleans the rows.
    - **The border.** `progress-values.ts` builds each `gameId` and `levelId` of a request with the builders: the sync body, the progress path, the leaderboard paths and the level update. `levelResultFrom()` checks the incoming bounds of the `levelId`, the stars, the moves and the time first, in the order of the fields, and then `buildLevelResult()` builds the result. The texts of the rules name the bounds, and `openapi/openapi.json` lists them as `minLength`, `maxLength` and `maximum`.
    - **Every border (decision 3 of #135, [2026-11-17](https://github.com/Hexablock-Suite/hexablock-api/issues/135#issuecomment-6953000419)).** The id bounds hold wherever a client sends an id, because the routes share the builders of `progress-values.ts`: one rule for an id, kept by its own builder. So the answers of routes that the issue did not name change: `GET /v1/progress/<65 chars>` goes from 404 to 400, `GET /v1/leaderboard/<65 chars>` from 200 to 400, a 65-character id in `GET /v1/leaderboard/:gameId/levels/:levelId` from 404 to 400, `PUT /v1/levels` with a 65-character or tab `levelId` from 204 to 400, and a NUL `levelId` in that path or in `PUT /v1/levels` from 500 to 400. An id of 64 characters keeps its answer. The rejected option kept the bounds only in `POST /v1/progress`: two rules for one id, and `PUT /v1/levels` would store a level whose id no sync can carry. No stored level has an id over 64 characters, so no level is orphaned. `test/progress-path-bounds.e2e-spec.ts` pins each route.

    Views 1.1 and 1.4 draw the four values with their `of()` factories; the bounds of the border appear in no view of the domain.

22. **The stars of a result against its level (built, [#135](https://github.com/Hexablock-Suite/hexablock-api/issues/135)).** Decided by Oscar on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) (question 3, DS-6): the most stars that a result can carry is the number of star thresholds of its level.
    - **The rule lives in the level.** `LevelSection` is the interface of every section: `mostStars()` gives the count of its star thresholds as a `Stars` value. `FitSection` and `SortSection` implement it, `LevelValidator<TSection extends LevelSection>` builds one, and `LevelDefinition.of()` takes only such a section. Since #222 the class `LevelDefinition` carries the same bound (decision 4). `LevelDefinition.isLevelOf(gameId, result)` tells if a result is a play of that level, `mostStars()` gives the count of its section, and `admits(result)` tells if the result carries no more stars than that count. `LevelResult` answers two boolean questions for them: `isFor(levelId)` and `hasMoreStarsThan(most)`. No getter leaves either aggregate.
    - **The use case reads the levels in one query and changes none (option C of [#217](https://github.com/Hexablock-Suite/hexablock-api/issues/217), decided by Oscar on 2026-11-26).** `SyncProgressUseCase` holds `LevelRepository` and reads the levels of all the results of a sync in one call of the port query `findFor(gameId, results)`. #171 added a level query on 2026-11-25, which reversed the decision of 2026-11-16 that the port gains no query and the sync reuses `list()`. #217 replaces that query, `find(gameId, result)`, which read one level per result, with this one batch query. The query takes the results, not a `LevelId`, because the use case cannot read the `LevelId` of a `LevelResult`: the domain has no getters (design decision of 2026-11-09), and rule R-no-delivery-call keeps `deliverTo()` out of layer 2. «No primitive crosses» is not the reason: a `LevelId` is already a value object, and `holds(gameId, levelId)` takes one. Each adapter receives the levelIds of the results in the border, through `receiveLevelResultOf()` of `src/adapters/received.ts`, and reads the rows of the `gameId` with an `IN` filter on those levelIds, so it reads no level that the results do not name (#171). `findFor()` gives the valid levels by levelId, each level once, and no level for an absent row or a broken row (decision 19), which holds no star thresholds. Before the lock of the progress, the use case pairs each result with its level through `isLevelOf()`, in the order of the request, and then asks `admits()`. A result with no paired level fails with `unknown-level`: no row, a row of another game, or a broken row. A result over the count fails with `too-many-stars`, which carries the result and the most stars. The first failure in the order of the results returns, and the use case saves nothing. A sync with no result calls no query, so Lines and Merge need no level. A new variant with level results needs its strategy and its stored levels first. The rejected options of #217: keep `find()` and fix only its reason, which keeps one sequential read per result; or give `LevelResult` an operation that hands its `LevelId` to layer 2, which rule R-no-delivery-call and decision 15 forbid.
    - **The border answers 400.** The body is wrong, not the route, so `ProgressController` turns both failures into a 400 with one detail: `No level <levelId> for gameId <gameId>.` and `stars of level <levelId> must be at most <most>, the count of its star thresholds, got <stars>.` The tests that sync a level result store the level first.

    Views 1.4, 2.2, 2.3 and slice 1 draw the change. View 1.2 draws a selection of the members of `LevelDefinition`, so it stays as it is; `classes.drawio` holds `LevelSection` and every new member.
