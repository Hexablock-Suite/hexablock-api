# Extensibility diagram

Status: draft for review with the team, 2026-10-31.

Statement §4 asks for an extensibility diagram with the engine in the center and the variants as extensions. Decision D6 and API-NFR-10 ask the API for the same standards and its own diagrams. The API has no game engine, so the application core sits in the center: `UseCase<TRequest, TResponse>` and the eight use cases. The extension points around it use the names of the [class diagram](classes.md). IDs such as D5, DS-6 and API-FR-04 refer to [`docs/REQUIREMENTS.md`](../REQUIREMENTS.md). The variation register (§8) and the decisions D4 and D5 are in the app repo's canonical `docs/REQUIREMENTS.md` (rule R-requirements). The file-by-file steps live in [`docs/EXTENSIBILITY.md`](../EXTENSIBILITY.md); this page draws the axes and does not repeat those steps.

## How to read it

- The colored zone is the Clean layer, with the colors of [layers.md](layers.md). The zones are bands, with the outer layer at the top and the inner layer at the bottom.
- The teal class is the extension point of the view. In view 1 it is `UseCase`, the contract of the application core.
- A dashed frame groups one extension axis or one pattern. Its label names the source, for example `DATABASE ENGINE · ADAPTER · §8`. No line starts or ends on a frame. When two classes of different groups depend on each other, the line joins those two classes, as each Drizzle repository in view 1 implements its own output port. A line from one frame to another frame would claim that every class of the first group uses every class of the second group. The professor asked this about a frame-to-frame arrow in the session of 2026-11-03: «todas esas usan los tres bloques de abajo, a lo mejor la respuesta es no».
- A box with a plural name, such as `HTTP controllers`, lists the exact class names in its compartment. A line to or from that box claims that every listed class has the relation, so the view draws one only when this is true, and the note of the view says so. In view 1, every controller holds 1 or 2 input ports, and every listed use case implements its input port. When only some listed classes have a relation, the view draws those classes as separate boxes, as `UpdateLevelsUseCase` and its `LevelValidators` in view 1.
- A dashed frame labelled `Aggregate` marks the boundary of one aggregate, as in the [class diagram](classes.md): the root and its members. Its dashes are longer and darker than the dashes of an axis frame. View 2 frames `LevelDefinition` with its section types. View 1 draws `LevelDefinition` with no member, so its frame encloses the root alone, and the footnote names the views of the class diagram that draw its members.
- A grey dashed box is a declared extension with no class yet. Its name is a placeholder. A grey italic member is a placeholder too.
- A white dashed box is a class that another view details, as in the class diagram.
- A realization arrow points from an extension class to the contract it implements. When several classes implement one contract, each class has its own dashed line, and the lines join into one arrowhead, as the drivers in view 1 and the validators in view 2 do. A `«bind»` label on it names the type that the extension gives to the type parameter. A filled diamond joins the root of an aggregate to each internal entity, with its multiplicity (classes of 2026-11-13 and 2026-11-14). A hollow diamond joins a decorator, an aspect included, to the type that it wraps, on the side of the decorator, labelled `decorate` with the multiplicity `1` (class of 2026-11-23). Every other attribute, another GoF pattern included, is a use arrow. Views 1 and 2 draw a use arrow `entries 0..*` where `LevelValidators` holds its strategies. A solid line with an open arrowhead is a use: its label names the attribute and its multiplicity, a value object included, as `LevelDefinition` holds its section in view 2, with one line to each section type, or a verb when the other class is only a parameter, a return value, a local variable or a `new` (class of 2026-11-02). The notation is the one of the [class diagram](classes.md), decision 13.
- The legend of each view lists only the line kinds that the view draws.
- When a use arrow starts at a box with a plural name, its label names the role and the multiplicity for one listed class, for example `input ports` and `1..2`.

## View 1: the core and its extension axes

![Overview: UseCase, which carries only «interface», and the nine use cases in the center of layer 2, with the four driver ports and the five output ports, and a use arrow levels 1 from UpdateLevelsUseCase to LevelRepository; around them the drivers, the HTTP controllers and the four Drizzle adapters in layer 3, where DrizzleLeaderboardReader implements GlobalBoardReader and LevelBoardReader (#218), the aspects in layer 2, and the level validators of layer 1, where LevelValidators holds LevelValidator through a use arrow entries 0..*, with the declared FillLevelValidator and the LevelDefinition aggregate root alone in a dashed Aggregate frame; the footnote says that UseCase is the contract that every input port binds, that LevelDefinition keeps its fields private, that FitSection and SortSection are value objects, that LeaderboardEntry is a response type of layer 2 and that Standing is a value object of layer 1, it says that a new variant with level files adds a section DTO in level.dto.ts and leaves the core unchanged, and it names LeaderboardDtoMapper and LevelDtoMapper, list(), findFor(gameId, results) and update(gameId, levelId, change) of LevelRepository and the LevelOrder, LevelVersion and Coordinate values of a level](extensibility/views/ext-1-overview.png)

Five axes surround the core. The drivers, the HTTP controllers and the database adapters sit in layer 3: every class that implements a port lives there ([#212](https://github.com/Hexablock-Suite/hexablock-api/issues/212), option C). The aspects sit in layer 2, next to the use cases they wrap (Q12). The level validators of each variant sit in layer 1. Every arrow from layer 3 points to the core, so a new driver, aspect, controller or database adapter adds a class and the core does not change. Each driver and each Drizzle repository implements one port, so each one has its own line to that port. The view draws only one port that a use case holds, the `LevelRepository` of `UpdateLevelsUseCase`, with a use arrow `levels 1`: views 2.2 to 2.4 of the class diagram draw the others, and the scenario [Database engine](#database-engine) draws the output ports with the declared MongoDB adapters. The core points inward to layer 1 only through `LevelValidators`, a domain service that the composition root fills. A new variant with level files adds two domain classes, its section and its strategy, registers the strategy there, and adds one section DTO in `src/adapters/http/level.dto.ts`. The section DTO is a change of the HTTP adapter. The core does not change (table [Extension points](#extension-points)). The HTTP controllers are the only input adapters of the code. The scenarios [Second protocol](#second-protocol) and [Web framework](#web-framework) declare a second transport and another web framework, so this view draws no placeholder for them.

## View 2: a new variant

![A new variant: the LevelDefinition aggregate root with its TSection, the section types FitSection and SortSection, which check their own shape and hold their rules, the root and the section types inside a dashed Aggregate frame, the LevelValidator strategy with FitLevelValidator and SortLevelValidator, which only pick their section type, FitLevelValidator, which finds the Topology of the level in Topologies, the LevelValidators domain service, which finds the strategy of a gameId with equals() and creates each level, and the declared FillSection and FillLevelValidator placeholders](extensibility/views/ext-2-new-variant.png)

The statement gives the example of a fifth variant: «por ejemplo, Hexa Fill: pintar celdas con restricciones» (§3.1). `FillSection` and `FillLevelValidator` are placeholders for it. They assume that Fill has level files; no source says so yet. The composition root registers `FillLevelValidator` for the `fill` game id in `levelValidators()`, and `src/adapters/http/level.dto.ts` gets a section DTO for Fill in the `oneOf` of `LevelDto.section`, so the OpenAPI schema describes the new section. The section DTO is a change of the HTTP adapter. The core does not change.

## Scenarios

A scenario shows one kind of change on the class model of the code: the extension points that it implements, the boxes that it adds, the files that it edits and the groups that stay the same. [`scenarios.json`](scenarios.json) lists the scenarios. The class diagram page draws each one, and its tool exports one image per scenario. The image keeps the bands of the page: layer 4 at the top and layer 1 at the bottom. A thick border marks an extension point. A dashed box in the focal color is an added box, and its name is a placeholder. A box with the mark `edited` sits in an edited file. A faded group holds an unchanged type. The side panel lists the edited files with their change, the added boxes, the extension points and the unchanged types.

The `Rpc` names and the folder `src/adapters/rpc/` are placeholders. Each handler holds the input ports that the HTTP controller of the same name holds, so the use cases do not change. [Open the scenario on the page](https://hexablock-suite.github.io/.github/#api~web-framework). No source of the repository declares another web framework: this scenario declares one. The change edits the 17 files of `src/adapters/http` that import `@nestjs`. Every DTO file is among them, because it imports `@nestjs/swagger`. The five files with no Nest import stay the same: the four DTO mappers and `progress-values.ts`. In layer 3 the change also edits `nest-logger.ts` of `src/adapters/logging` and `jwt-token-issuer.ts` of `src/adapters/jwt`. In layer 4 the change is more than the wiring of `app.module.ts`: `http-app.ts`, `database.module.ts`, `connection.ts`, `auth-config.ts` and `src/main.ts` change too. The rules `http-adapters-import-only-nest`, `jwt-adapters-import-only-nest-jwt` and `logging-adapters-import-only-nest-common` of `.dependency-cruiser.cjs` and `package.json` name the new packages. The persistence adapter, the use cases and the domain do not change: no file there imports `@nestjs`, and the rule `persistence-adapters-never-import-nest` keeps it so.

## Render the images

The views come from the HTML files in [`extensibility/views/`](extensibility/views/). They follow the same rules as the [class diagram](classes.md): each file holds one inline SVG drawn with the diagram-design skill and the HexaBlock profile. Open the file in a browser to see the drawing. The `.png` image next to it is that SVG rendered at scale 2 by a headless browser, in the page width that [«Render the images» of classes.md](classes.md#render-the-images) gives. After you edit a file, export the image again with `/diagram-design:export-diagram docs/architecture/extensibility/views/<view>.html --png-only`, then run `pnpm format`. Commit each `.html` file together with its `.png` image.

The scenario images in [`extensibility/scenarios/`](extensibility/scenarios/) come from the tool `drawio-clases` of [Hexablock-Suite/.github](https://github.com/Hexablock-Suite/.github/tree/main/tools/drawio-clases), not from a hand-made file. Nobody edits them by hand. After a change of [`scenarios.json`](scenarios.json) or of a type that a scenario names, make them again from a clean clone of this repository with the commands of the section «Scenario images» of the tool README: `merge.mjs`, `scenarios.mjs`, `page/build.mjs` and `page/export.mjs`. Then copy each `api-<id>.png` to `extensibility/scenarios/<id>.png`. `scenarios.mjs` stops a scenario that names a type that the code no longer has.
