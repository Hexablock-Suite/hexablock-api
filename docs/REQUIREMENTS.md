# Requirements (backend view)

This file holds the backend requirements, written in our own words. The canonical document for the whole project, with the variation register, every assumption and every question for the professor, is [`hexablock-app/docs/REQUIREMENTS.md`](https://github.com/Hexablock-Suite/hexablock-app/blob/main/docs/REQUIREMENTS.md). Keep the IDs (A#, Q#, C#) the same in both files.

- **Source:** the course statement "Proyecto Semestral — HexaBlock Suite", version 1.0, issued 2026-10-23. It is not redistributed in this repository. Each item cites its section as `§n`.
- **Requirement IDs:** **API-FR-n** is a functional requirement: what the API serves. **API-NFR-n** is a non-functional requirement: how the backend is built, tested and documented. The client uses APP-FR-n and APP-NFR-n; its APP-FR-12 to APP-FR-15 are the client side of API-FR-01 to API-FR-04. An ID never changes; a dropped requirement keeps its ID and says "Dropped".
- **Checks:** each requirement ends with _Check_, the evidence that shows it is met. Where a gate already exists, the check names it. The other checks are a proposal of 2026-10-30 for the team to review.
- **Business rules:** the type, the owner and the layer of each business rule of this file are in the table «Business rules» of [`architecture/classes.md`](architecture/classes.md#business-rules).
- **Rule:** when a backend requirement, an assumption or an answer from the professor changes, update this file and the canonical one in the same pair of pull requests.

## 1. What the backend serves (functional, §2, §5.2)

A REST API that manages users, progress, scores and level definitions for the four variants: Hexa Lines, Hexa Fit, Hexa Sort and Hexa Merge. Every variant is identified by a `gameId`.

API-FR-01 to API-FR-06 keep the numbers of statement §5.2.

- **API-FR-01 — Sign-up and sign-in (§5.2.1).** Sign-up and sign-in with JWT. A username is stored as the player typed it. Sign-up rejects a username that differs from a stored one only in letter case (`Ada` after `ada`) with the same 409 as an exact duplicate, and a unique index on `lower(username)` holds the rule when two sign-ups run at the same time. Sign-in looks the user up by the same lower-case key that sign-up uses, so `ADA`, `Ada` and `ada` sign in the stored `ada` with its password, and the stored name keeps the letter case of sign-up (decided on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134), built in [#144](https://github.com/Hexablock-Suite/hexablock-api/issues/144); it replaces the as-typed sign-in of [#62](https://github.com/Hexablock-Suite/hexablock-api/issues/62)). _Check:_ an e2e test signs up, signs in and calls a protected endpoint with the token; the same call without a token gets 401.
- **API-FR-02 — Progress sync (§5.2.2).** Progress sync with `gameId` as a required key: one progress entry per user and per variant. _Check:_ an endpoint test saves progress for two variants and reads back two entries; a second save for the same user and variant does not add an entry; a request without `gameId` is rejected. When two results of one level arrive, DS-12 decides which one stays. Built on [#135](https://github.com/Hexablock-Suite/hexablock-api/issues/135): a value that a client sends has bounds, and a value outside them gets 400 with the error body of API-FR-06 and the text of its rule, and the API stores nothing. A `gameId` and a `levelId` hold 1 to 64 characters, and a `levelId` holds no control character (U+0000 to U+001F, U+007F); the same bounds apply to the paths of the progress and leaderboard routes and to the level update (API-FR-04), as decision 3 of #135 states ([2026-11-17](https://github.com/Hexablock-Suite/hexablock-api/issues/135#issuecomment-6953000419)): one rule for an id, at every border where a client sends one. So `GET /v1/progress/:gameId`, `GET /v1/leaderboard/:gameId`, `GET /v1/leaderboard/:gameId/levels/:levelId` and `PUT /v1/levels` answer 400 with the error body of API-FR-06 for an id outside the bounds, a NUL `levelId` included, which answered 500 before; an id of 64 characters keeps its answer. `test/progress-path-bounds.e2e-spec.ts` pins each route. The `stars` and the `moves` of one result are at most 2147483647, the largest value of their integer columns. A row stored before these bounds keeps its values and still reads, and a total of the global leaderboard can exceed one column.
- **API-FR-03 — Leaderboard (§5.2.3).** A global leaderboard per `gameId` and, for the level-based variants (Fit and Sort), per level. _Check:_ an endpoint test filters by `gameId` and by level. DS-4 orders the per-level leaderboard, and S3-03 orders the global one (§4). Decided on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) and built on [#146](https://github.com/Hexablock-Suite/hexablock-api/issues/146): the leaderboard of a level that the level definitions do not hold answers 404 with the error body of API-FR-06, because the API holds every level (A6, API-FR-04). An unknown `levelId`, an unknown `gameId` and a `levelId` of another `gameId` each get 404, also when a player has synced a result for it. A stored level has a leaderboard, empty while no player has a result; a stored row that breaks a rule is still a stored level. The global leaderboard of a `gameId` keeps its answer: any `gameId` has one, empty while no player has a result.
- **API-FR-04 — Level definitions (§5.2.4).** Read and update the level definitions of Fit and Sort, so new levels reach players without an app update. One generic level schema, with a section specific to each `gameId`. _Check:_ an endpoint test reads the levels of each `gameId`, and the update rejects a Fit level that fails A5. Who may update levels is Q4: on 2026-11-03 the update endpoint kept the token guard only, with no roles. Decided on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) and on 2026-11-17 on [#145](https://github.com/Hexablock-Suite/hexablock-api/issues/145) (built): `PUT /v1/levels` needs the token and an account in the list of level editors of the configuration, `LEVEL_EDITOR_IDS`, which holds user ids, not usernames. Any other signed-in account gets 403 with the error body of API-FR-06, and the API saves nothing. An empty or unset list lets no account update (fail closed). No role model: no role column and no role claim in the token. An update reaches players only when it raises the level `version` (DS-11). A stored level row that breaks a rule, decided on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) and on 2026-11-17 on [#147](https://github.com/Hexablock-Suite/hexablock-api/issues/147) (built): `PUT /v1/levels` replaces that row with a valid level of the same `gameId` and `levelId`. The version rule of S3-10 still holds when the row keeps a valid `version`: an equal or a higher version replaces the row, and a lower version saves nothing and gets `older-version`. When the stored `version` itself breaks its rule, any valid version replaces the row. `GET /v1/levels` answers 200 with the other levels in `levels`, and the optional field `unavailable` names each broken row with its `gameId`, `levelId` and `reason`, the code of its first broken rule; the field is absent when no row is broken. The API logs one entry per broken row with the same three values. The API holds every level, the levels that the app bundles too (A6), as decided on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134): a level that the API does not hold has no leaderboard (API-FR-03, built on [#146](https://github.com/Hexablock-Suite/hexablock-api/issues/146)). Not built yet ([#158](https://github.com/Hexablock-Suite/hexablock-api/issues/158)): a deploy step sends the bundled level files of the app to `PUT /v1/levels` before the first request asks a leaderboard, and a check flags a bundled file that differs from the stored copy.
- **API-FR-05 — API documentation (§5.2.5).** API documentation with Swagger/OpenAPI. _Check:_ `pnpm openapi:export` writes `openapi/openapi.json`, and `test/health.e2e-spec.ts` fails when the committed file differs from the code (rule R-openapi-drift).
- **API-FR-06 — HTTP errors (§5.2.6).** Consistent HTTP error responses. _Check:_ e2e tests for a validation error, a missing token and a missing resource get the same body shape.

- **API-NFR-09 — GoF patterns (§3.3).** Required here too: the patterns the design needs, each one justified. See decision D7 in the client requirements. _Check:_ the README section "Design Patterns" lists each pattern used with its justification and a link to its file.
- **API-NFR-10 — Diagrams and extensibility (§4).** Required here too: the class and layer diagrams and `EXTENSIBILITY.md` in `docs/` (D6). _Check:_ [`architecture/layers.md`](architecture/layers.md) holds the layer diagram and [`architecture/classes.md`](architecture/classes.md) holds the class diagram; [`architecture/extensibility.md`](architecture/extensibility.md) holds the extensibility diagram; [`EXTENSIBILITY.md`](EXTENSIBILITY.md) says, for each extension axis of that diagram, which class a developer adds and which file registers it. Notation (classes of 2026-11-02, 2026-11-13, 2026-11-14 and 2026-11-23): an attribute across layers, a parameter, a return value, a local variable or a `new` is a use arrow, labelled with the attribute and its multiplicity or with a verb; a diagram draws a filled diamond only from the root of an aggregate to each of its internal entities, with its multiplicity; a decorator, an aspect included, joins the type that it wraps with a hollow diamond on the side of the decorator, labelled `decorate` with the multiplicity `1`; any other attribute, a value object or another GoF pattern included, is a use arrow with its role and multiplicity. See decision 13 of [`architecture/classes.md`](architecture/classes.md).
- **API-NFR-11 — Reproducible core (D6).** `src/application` reads time from the `Clock` port in `src/application/ports/clock.ts`, and `src/domain` takes the instant as a parameter, because ports live in the application layer and the domain never imports it. Both layers take randomness from an injected seeded source. _Check:_ gate `test/gates/determinism.gate.spec.ts` (rule R-deterministic-core).
- **API-NFR-12 — README (§6.1).** The README is required in this repository too. _Check:_ gate `test/gates/docs-skeleton.spec.ts` (rule R-docs-skeleton).
- **API-NFR-13 — Commits (§6.2).** Conventional Commits are required in this repository too. _Check:_ `commitlint.config.cjs`, the commit-msg hook and gate `test/gates/commit-message.gate.spec.ts` (rule R-conventional-commits).
- **API-NFR-14 — AI usage (§7).** `AI_USAGE.md` is required in this repository too. _Check:_ no gate (rule R-ai-usage-log); each pull request adds its entry.
- **API-NFR-15 — Route version (§5.2).** The API serves every route under the URI version prefix `/v1`, applied with `setGlobalPrefix('v1')` in `configureHttpApp` ([#173](https://github.com/Hexablock-Suite/hexablock-api/issues/173)): `/v1/health`, `/v1/auth/...`, `/v1/progress/...`, `/v1/leaderboard/...` and `/v1/levels`. No other form of HTTP versioning: no header, no media type and no query parameter, and the prefix is exactly `v1`, never `/api/v1`. The Swagger UI and its JSON document stay at `/docs` and `/docs-json`, outside the versioned surface. Oscar delegated the choice to the API team, and Kelvin decided it on 2026-11-23, before the app shipped against the routes, so no client ever consumed the unversioned paths. The prefix is part of the HTTP contract: a future change that breaks the contract needs an explicit migration and version decision, coordinated between this API, the app client and the pact in the same step. Adding engine content, a new figure or new level files does not create a new HTTP contract version by itself. This version is not the release version of a sprint tag (`v0.N.0`), not the level `version` of S3-10 and DS-11, and not the version of a local progress copy. _Check:_ every route of `openapi/openapi.json` starts with `/v1`, the e2e suite requests the prefixed routes, and `scripts/contract/verify-provider.js` verifies the prefixed `/v1/health` of the client pact.

## 3. Assumptions that shape the API

- **A5 — Fit levels can be won.** Every Fit level carries the designer's solution (piece, rotation, position). The rotation counts steps of the level's topology, never degrees: the hexagonal topology has six steps of 60°, and another topology gives its own steps (D4). The level update endpoint rejects a Fit level when its pieces do not have the same total area as the figure, or when the stored solution does not cover the figure exactly without overlaps. Pieces rotate; they are never mirrored. The rotation rule is confirmed on 2026-11-03 (C7).
- **A6 — Level origin.** The app always ships its own levels and works offline; levels from this API add to them or replace them. The API is not required for a first launch. When the app and this API hold the same level, DS-11 decides which copy wins. Decided on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134); not built yet: the API holds every level, the ones that the app bundles too. The bundled JSON files of the app (`src/adapters/levels/` of hexablock-app) reach the API through `PUT /v1/levels` at each deploy. The one level format of S3-02 lets the files go as they are. A check flags a bundled file that differs from the stored copy.
- **A7 — Public repositories.** This repository is public.
- **A9 — Backend scope.** Replaced on 2026-10-26 by the client's D6: this backend meets the same standards as the client (generics, SOLID, Clean Architecture, the patterns it needs, `EXTENSIBILITY.md` and its own class and layer diagrams in `docs/`). The class diagram exists since 2026-10-31: [`architecture/classes.md`](architecture/classes.md). The extensibility diagram exists since 2026-10-31: [`architecture/extensibility.md`](architecture/extensibility.md). `EXTENSIBILITY.md` exists since 2026-11-17: [`EXTENSIBILITY.md`](EXTENSIBILITY.md).

## 4. Data shape decisions (team)

- **DS-5 — Progress shape (§5.2.2, §5.2.3).** Closed by the team on 2026-10-30 with option «B · Dos tablas»: one progress row per `userId` and `gameId`, and a level results table with `userId`, `gameId`, `levelId`, `stars`, `moves` and `elapsedMs`. The per-level leaderboard reads the level results table. In the domain, `PlayerProgress` is the aggregate root and keeps its level results; one repository saves both tables. See [`architecture/classes.md`](architecture/classes.md), views 1.1 and 3.1.
- **DS-4 — Leaderboard order (§5.2.3).** Closed by the team on 2026-11-06 ([#24](https://github.com/Hexablock-Suite/hexablock-api/issues/24)). One order ranks the results of a level: more `stars` wins; on equal stars, fewer `moves` wins; on equal moves, less `elapsedMs` wins. On a full tie, the stored result stays. The reason: a player never loses a best result. This order decides which result the level results table keeps (DS-12), and it orders the per-level leaderboard of Fit and Sort, because both variants give stars (DS-6, [Hexablock-Suite/hexablock-app#59](https://github.com/Hexablock-Suite/hexablock-app/issues/59)). Scoring is defined by the team (§5.1.6). DS-12 closed the every-attempt question on 2026-11-06: only the best one. _Check:_ domain unit tests rank each step of the order, and a full tie keeps the stored result.
- **S3-03 — Global leaderboard order (§5.2.3).** Confirmed on 2026-11-16 on [#76](https://github.com/Hexablock-Suite/hexablock-api/issues/76). Lines and Merge rank by `highScore`: the higher score wins. Fit and Sort rank by more total `stars`, then more levels completed, then fewer total `moves`, then less total `elapsedMs`. The totals add up the level results table, which keeps one result per level (DS-12). The reason: Fit gives no points per turn (client D22), so only the stars can rank it, and its `highScore` never ranks the Fit board. Levels completed come before moves, because the sum of moves grows with each level played. Moves and then time follow DS-4, applied to the totals. _Check:_ domain unit tests rank each step of the order, and a full tie ranks neither player first.
- **DS-6 — Level schema (§5.2.4).** Closed by the team on 2026-10-30 with option «A · Común + sección tipada»: a common part (`gameId`, `levelId`, `order`, `version`, `topology`) and a typed section per `gameId`, validated per variant. The Fit section has `figure`, `pieces`, `witness` (the solution of A5) and `stars`, an ordered list of star thresholds, each one `{ maxMoves, maxElapsedMs }`; a Fit star needs both of its thresholds ([Hexablock-Suite/hexablock-app#60](https://github.com/Hexablock-Suite/hexablock-app/issues/60), client D22). The Sort section has `radius`, `goals`, `source` and `stars`, an ordered list of star thresholds, each one a `maxMoves` count. The team chose stars by moves for Sort on 2026-11-06 ([Hexablock-Suite/hexablock-app#59](https://github.com/Hexablock-Suite/hexablock-app/issues/59), client D22). The stars of both sections are cumulative: star N needs star N-1, so a play gets one star for each leading threshold that it meets (client D22). Decided on 2026-11-16 on [#134](https://github.com/Hexablock-Suite/hexablock-api/issues/134) and built on [#135](https://github.com/Hexablock-Suite/hexablock-api/issues/135): the most stars that a result can carry is the number of star thresholds of its level, and the API checks the stars of a result against its level. `POST /v1/progress` answers 400 with the error body of API-FR-06 and stores nothing when a result carries more stars than its level has star thresholds, and when the API holds no valid level of a result: no stored level of that `gameId` and `levelId`, or a stored row that breaks a rule. A result with as many stars as thresholds is stored. A sync with no result, as Lines and Merge send, needs no level. The API rejects a Fit level that fails A5 (API-FR-04). The Fit check reads the rotation steps from the topology that the `topology` field names, so the API accepts a level of any topology that the code knows; it does not reject a topology only because it is not hexagonal. See [`architecture/classes.md`](architecture/classes.md), views 1.2 and 2.3, decision 6.
- **DS-11 — Level version (§5.1.5, §5.2.4, A6).** Closed by the team on 2026-11-06. The app can hold two copies of one level: the bundled copy and a copy from this API. Both copies have the same `gameId` and `levelId`. The copy with the higher `version` wins. When the versions are equal, the app uses the bundled copy. A `levelId` that only this API has adds a level. So a level update reaches players only when it raises `version`. The app applies this rule (client APP-FR-15). _Check:_ a client test gives the level repository a bundled copy and an API copy of one level, and the copy with the higher `version` loads.
- **DS-12 — Best result per level (§5.2.2, §5.2.3).** Closed by the team on 2026-11-06 with option «El mejor resultado». One account can send two results for one level: from two devices, from a device that syncs late after offline play, or after the player plays the level again. The level results table keeps one row per `userId`, `gameId` and `levelId`, and that row is the best result. DS-4 decides which result is the best. The high score in the progress row follows the same rule: the highest one stays. So the order of the syncs does not change the stored results or the high score. A repeated sync of one result changes no stored result and no high score, and `updatedAt` records the instant of that sync (decision 3 of [`architecture/classes.md`](architecture/classes.md)). The domain keeps the best result by the order of DS-4, and the repository saves what the domain keeps. _Check:_ a use case test syncs a better result and then a worse one for the same level, and the better one stays; the same test in the opposite order stores the same row.
- **S3-02 — Level file format (§5.2.4).** Confirmed on 2026-11-16 on [#76](https://github.com/Hexablock-Suite/hexablock-api/issues/76). The app and the API share one JSON level format: [`level-format.md`](level-format.md) gives the fields of DS-6, their rules and one complete example per variant. `GET /v1/levels` answers each level in this format, and `PUT /v1/levels` takes it ([#81](https://github.com/Hexablock-Suite/hexablock-api/issues/81)). The reason: the app reads its level files and the levels of this API in one format, and DS-11 compares two copies of one level more simply when both use it. Each repository maps the format to its own domain model in an adapter: the app in `src/adapters/bundled-level-repository.ts`, the API in its HTTP DTO mapper. Only the exchange format is shared, never a domain class. _Check:_ the level tests read their fixtures from the complete examples of the format, and an endpoint test reads back the levels that it updated, field for field.
- **S3-10 — Level version on update (§5.2.4, DS-11).** Confirmed on 2026-11-16 on [#76](https://github.com/Hexablock-Suite/hexablock-api/issues/76). `PUT /v1/levels` rejects a level whose `version` is lower than the version of the stored copy, with the level problem `older-version`, and it accepts an equal or a higher `version`. The reason: a level never goes back to an older copy, and a repeated batch stays idempotent. DS-11 says which copy wins in the app, not what the API accepts. `LevelDefinition.accepts()` holds the rule, and `LevelRepository.update()` runs it under the lock of the level, so an update that races another one cannot save an older copy ([#80](https://github.com/Hexablock-Suite/hexablock-api/issues/80), [#81](https://github.com/Hexablock-Suite/hexablock-api/issues/81)). _Check:_ an endpoint test rejects a lower `version` and accepts an equal one.
