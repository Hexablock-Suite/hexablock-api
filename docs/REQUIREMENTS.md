# Requirements (backend view)

This file holds the backend requirements, written in our own words. The canonical document for the whole project, with the variation register, every assumption and every question for the professor, is [`hexablock-app/docs/REQUIREMENTS.md`](https://github.com/Hexablock-Suite/hexablock-app/blob/main/docs/REQUIREMENTS.md). Keep the IDs (A#, Q#, C#) the same in both files.

- **Source:** the course statement "Proyecto Semestral — HexaBlock Suite", version 1.0, issued 2026-10-23. It is not redistributed in this repository. Each item cites its section as `§n`.
- **Requirement IDs:** **API-FR-n** is a functional requirement: what the API serves. **API-NFR-n** is a non-functional requirement: how the backend is built, tested and documented. The client uses APP-FR-n and APP-NFR-n; its APP-FR-12 to APP-FR-15 are the client side of API-FR-01 to API-FR-04. An ID never changes; a dropped requirement keeps its ID and says "Dropped".
- **Checks:** each requirement ends with _Check_, the evidence that shows it is met. Where a gate already exists, the check names it. The other checks are a proposal of 2026-10-30 for the team to review.
- **Rule:** when a backend requirement, an assumption or an answer from the professor changes, update this file and the canonical one in the same pair of pull requests.

## 1. What the backend serves (functional, §2, §5.2)

A REST API that manages users, progress, scores and level definitions for the four variants: Hexa Lines, Hexa Fit, Hexa Sort and Hexa Merge. Every variant is identified by a `gameId`.

API-FR-01 to API-FR-06 keep the numbers of statement §5.2.

- **API-FR-01 — Sign-up and sign-in (§5.2.1).** Sign-up and sign-in with JWT. A username is stored as the player typed it. Sign-up rejects a username that differs from a stored one only in letter case (`Ada` after `ada`) with the same 409 as an exact duplicate, and a unique index on `lower(username)` holds the rule when two sign-ups run at the same time. Sign-in compares the name as typed, so `ADA` does not sign in the stored `ada` ([#62](https://github.com/Hexablock-Suite/hexablock-api/issues/62)). _Check:_ an e2e test signs up, signs in and calls a protected endpoint with the token; the same call without a token gets 401.
- **API-FR-02 — Progress sync (§5.2.2).** Progress sync with `gameId` as a required key: one progress entry per user and per variant. _Check:_ an endpoint test saves progress for two variants and reads back two entries; a second save for the same user and variant does not add an entry; a request without `gameId` is rejected. When two results of one level arrive, DS-12 decides which one stays.
- **API-FR-03 — Leaderboard (§5.2.3).** A global leaderboard per `gameId` and, for the level-based variants (Fit and Sort), per level. _Check:_ an endpoint test filters by `gameId` and by level. What orders the per-level leaderboard is still open (§4).
- **API-FR-04 — Level definitions (§5.2.4).** Read and update the level definitions of Fit and Sort, so new levels reach players without an app update. One generic level schema, with a section specific to each `gameId`. _Check:_ an endpoint test reads the levels of each `gameId`, and the update rejects a Fit level that fails A5. Who may update levels is Q4, answered on 2026-11-03: the update endpoint keeps the token guard only, with no roles. An update reaches players only when it raises the level `version` (DS-11).
- **API-FR-05 — API documentation (§5.2.5).** API documentation with Swagger/OpenAPI. _Check:_ `pnpm openapi:export` writes `openapi/openapi.json`, and `test/health.e2e-spec.ts` fails when the committed file differs from the code (rule R-openapi-drift).
- **API-FR-06 — HTTP errors (§5.2.6).** Consistent HTTP error responses. _Check:_ e2e tests for a validation error, a missing token and a missing resource get the same body shape.

## 2. Quality requirements that reach the backend (non-functional)

- **API-NFR-01 — Unit tests (§3.6).** Unit tests with mocks or stubs. Names follow `should_[result]_when_[condition]` with Arrange-Act-Assert. _Check:_ gate `test/gates/test-name.gate.spec.ts` (rule R-test-names).
- **API-NFR-02 — Integration tests (§3.6).** Integration tests of use cases with real repositories on an in-memory database. _Check:_ repository tests run on PGlite through `test/support/test-database.ts`, and gate `test/integration/in-memory-database.spec.ts` covers the harness (rule R-database-harness). The advisory-lock suite also runs on a throwaway Postgres in the CI job `postgres-lock`, because PGlite cannot show two sessions.
- **API-NFR-03 — Endpoint tests (§3.6).** Endpoint tests with an HTTP test client, including filtering by `gameId`; save and load progress end to end for each variant. _Check:_ the e2e suite has one save-and-load test per variant.
- **API-NFR-04 — Contract tests (§3.6).** Pact contract tests (recommended). _Check:_ the CI `contract` job runs `scripts/contract/verify-provider.js` against the client's pact (rule R-contract).
- **API-NFR-05 — CI (§3.6).** CI on every pull request. _Check:_ the CI `verify` job runs on every pull request, and gate `test/gates/ci-contract.spec.ts` keeps it in step with `pnpm verify` (rule R-verify-parity).
- **API-NFR-06 — SOLID (§3.2).** SOLID applies to all project code; each principle used has a README example from this repo. _Check:_ the README section "SOLID Principles" has one example per principle with a link to its file.
- **API-NFR-07 — AOP (§3.5).** Aspects are decorators or proxies over use cases, never inside business code. _Check:_ gate `test/gates/architecture.gate.spec.ts` keeps Nest out of `src/application` (rule R-application-pure), and a test shows the aspect runs while the use case it wraps has none of its code.
- **API-NFR-08 — Clean Architecture (§3.4).** Required here too. See decision D6 in the client requirements. In the session of 2026-11-03 the professor named the valid hybrid: Clean plus an architecture made for games, not Hexagonal plus Clean: «no, no, entre hexagonal y clean, perdón, entre clean y alguna arquitectura particular para juegos». Every part of the project follows the layers, the backend included. Ports and adapters stay, as Clean vocabulary. _Check:_ `pnpm arch` and gate `test/gates/architecture.gate.spec.ts` (rules R-domain-pure, R-application-pure, R-persistence-no-nest, R-adapters-no-infrastructure); the layer diagram is in [`architecture/layers.md`](architecture/layers.md).
- **API-NFR-09 — GoF patterns (§3.3).** Required here too: the patterns the design needs, each one justified. See decision D7 in the client requirements. _Check:_ the README section "Design Patterns" lists each pattern used with its justification and a link to its file.
- **API-NFR-10 — Diagrams and extensibility (§4).** Required here too: the class and layer diagrams and `EXTENSIBILITY.md` in `docs/` (D6). _Check:_ [`architecture/layers.md`](architecture/layers.md) holds the layer diagram and [`architecture/classes.md`](architecture/classes.md) holds the class diagram; [`architecture/extensibility.md`](architecture/extensibility.md) holds the extensibility diagram; `docs/EXTENSIBILITY.md` is still to write. ## 3. Assumptions that shape the API

- **A5 — Fit levels can be won.** Every Fit level carries the designer's solution (piece, rotation, position). The rotation counts steps of the level's topology, never degrees: the hexagonal topology has six steps of 60°, and another topology gives its own steps (D4). The level update endpoint rejects a Fit level when its pieces do not have the same total area as the figure, or when the stored solution does not cover the figure exactly without overlaps. Pieces rotate; they are never mirrored. The rotation rule is confirmed on 2026-11-03 (C7).
- **A6 — Level origin.** The app always ships its own levels and works offline; levels from this API add to them or replace them. The API is not required for a first launch. When the app and this API hold the same level, DS-11 decides which copy wins.
- **A7 — Public repositories.** This repository is public.
- **A9 — Backend scope.** Replaced on 2026-10-26 by the client's D6: this backend meets the same standards as the client (generics, SOLID, Clean Architecture, the patterns it needs, `EXTENSIBILITY.md` and its own class and layer diagrams in `docs/`). The class diagram exists since 2026-10-31: [`architecture/classes.md`](architecture/classes.md). The extensibility diagram exists since 2026-10-31: [`architecture/extensibility.md`](architecture/extensibility.md).

## 4. Data shape decisions (team)

- **DS-5 — Progress shape (§5.2.2, §5.2.3).** Closed by the team on 2026-10-30 with option «B · Dos tablas»: one progress row per `userId` and `gameId`, and a level results table with `userId`, `gameId`, `levelId`, `stars`, `moves` and `elapsedMs`. The per-level leaderboard reads the level results table. In the domain, `PlayerProgress` is the aggregate root and keeps its level results; one repository saves both tables. See [`architecture/classes.md`](architecture/classes.md), views 1.1 and 3.1.
- **DS-4 — Leaderboard order (§5.2.3).** Closed by the team on 2026-11-06 ([#24](https://github.com/Hexablock-Suite/hexablock-api/issues/24)). One order ranks the results of a level: more `stars` wins; on equal stars, fewer `moves` wins; on equal moves, less `elapsedMs` wins. On a full tie, the stored result stays. The reason: a player never loses a best result. This order decides which result the level results table keeps (DS-12), and it orders the per-level leaderboard of Fit and Sort, because both variants give stars (DS-6, [Hexablock-Suite/hexablock-app#59](https://github.com/Hexablock-Suite/hexablock-app/issues/59)). Scoring is defined by the team (§5.1.6). DS-12 closed the every-attempt question on 2026-11-06: only the best one. _Check:_ domain unit tests rank each step of the order, and a full tie keeps the stored result.
- **DS-6 — Level schema (§5.2.4).** Closed by the team on 2026-10-30 with option «A · Común + sección tipada»: a common part (`gameId`, `levelId`, `order`, `version`, `topology`) and a typed section per `gameId`, validated per variant. The Fit section has `figure`, `pieces`, `witness` (the solution of A5) and `stars`, an ordered list of star thresholds, each one `{ maxMoves, maxElapsedMs }`; a Fit star needs both of its thresholds ([Hexablock-Suite/hexablock-app#60](https://github.com/Hexablock-Suite/hexablock-app/issues/60), client D22). The Sort section has `radius`, `goals`, `source` and `stars`, an ordered list of star thresholds, each one a `maxMoves` count. The team chose stars by moves for Sort on 2026-11-06 ([Hexablock-Suite/hexablock-app#59](https://github.com/Hexablock-Suite/hexablock-app/issues/59), client D22). The stars of both sections are cumulative: star N needs star N-1, so a play gets one star for each leading threshold that it meets (client D22). The API rejects a Fit level that fails A5 (API-FR-04). The Fit check reads the rotation steps from the topology that the `topology` field names, so the API accepts a level of any topology that the code knows; it does not reject a topology only because it is not hexagonal. See [`architecture/classes.md`](architecture/classes.md), views 1.2 and 2.3, decision 6.
- **DS-11 — Level version (§5.1.5, §5.2.4, A6).** Closed by the team on 2026-11-06. The app can hold two copies of one level: the bundled copy and a copy from this API. Both copies have the same `gameId` and `levelId`. The copy with the higher `version` wins. When the versions are equal, the app uses the bundled copy. A `levelId` that only this API has adds a level. So a level update reaches players only when it raises `version`. The app applies this rule (client APP-FR-15). _Check:_ a client test gives the level repository a bundled copy and an API copy of one level, and the copy with the higher `version` loads.
- **DS-12 — Best result per level (§5.2.2, §5.2.3).** Closed by the team on 2026-11-06 with option «El mejor resultado». One account can send two results for one level: from two devices, from a device that syncs late after offline play, or after the player plays the level again. The level results table keeps one row per `userId`, `gameId` and `levelId`, and that row is the best result. DS-4 decides which result is the best. The high score in the progress row follows the same rule: the highest one stays. So the order of the syncs does not change the stored progress, and a repeated sync of one result changes nothing. The domain keeps the best result by the order of DS-4, and the repository saves what the domain keeps. _Check:_ a use case test syncs a better result and then a worse one for the same level, and the better one stays; the same test in the opposite order stores the same row.
